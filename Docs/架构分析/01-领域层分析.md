# 领域层（Domain Layer）分析

> 整洁架构的核心：零依赖的纯领域模型，包含业务规则和领域逻辑

## 1. 领域层概述

领域层是整个系统的**核心**，包含：
- **实体（Entity）**：有唯一标识的业务对象
- **值对象（Value Object）**：无唯一标识，通过属性值判断相等性
- **端口（Port）**：定义外部依赖的接口（在 usecase/port 目录）

**设计原则**：
- 零框架依赖：不 import gorm/jwt/llm 等外部库
- 纯 Go struct + 领域规则方法
- 业务规则内聚在实体内部

## 2. 核心实体分析

### 2.1 Brand（品牌实体）

**位置**：`internal/domain/entity/geo.go`

**业务定位**：GEO 业务的聚合根，商户的品牌资产

```go
type Brand struct {
    ID           string
    TenantID     string   // 租户隔离
    Name         string   // 品牌名
    Positioning  string   // 品牌定位（生成内容的提示词语料）
    CoreSelling  []string // 核心卖点
    Competitors  []string // 竞品名清单
    BizType      string   // 业务类型：local/online
    Industry     string   // 行业
    WebsiteURL   string   // 官网地址
    CreatedAt    time.Time
}
```

**领域规则**：
- `IsValid()`：品牌必须有 ID、TenantID、Name
- `IsLocal()`：判断是否为本地生意（默认 local，空值兼容）

**业务语义**：
- **BizType 分流**：
  - `local`：本地生意，需要门店档案、附近同行、本地问法、NAP 内容
  - `online`：线上业务，跳过门店/附近同行，使用品类问法、行业竞品蒸馏

### 2.2 StoreLocation（门店位置实体）

**业务定位**：本地生活 GEO 的地基，物理位置信息

```go
type StoreLocation struct {
    ID           string
    TenantID     string
    BrandID      string
    Name         string   // 门店名
    Address      string   // 详细地址
    City         string   // 城市
    District     string   // 区/县
    Adcode       string   // 行政区划代码
    Lat          float64  // 纬度
    Lng          float64  // 经度
    Phone        string   // 联系电话
    Hours        string   // 营业时间
    PriceLevel   string   // 人均消费档位
    BizType      string   // 业态（LocalBusiness/Restaurant/Cafe...）
    BusinessArea string   // 所属商圈
    GeoStatus    string   // 地理编码状态：pending/ok/failed
    CreatedAt    time.Time
    UpdatedAt    time.Time
}
```

**领域规则**：
- `IsValid()`：门店必须有 ID、TenantID、BrandID、Address
- `HasGeo()`：判断是否已有可用的地理编码结果（GeoStatus=ok 且 Lat/Lng 非零）

**设计要点**：
- Lat/Lng/City/District/Adcode 由地理编码服务（GeoLocator 适配器）回填
- 实体层不依赖任何地图 SDK——纯数据 + 领域规则
- GeoStatus 标记编码状态，支持重试机制

### 2.3 Keyword（关键词实体）

**业务定位**：商户要监测/优化的搜索词

```go
type Keyword struct {
    ID        string
    TenantID  string
    BrandID   string    // 所属品牌
    Term      string    // 关键词（如"北京装修公司哪家好"）
    Intent    string    // 搜索意图：informational/transactional/local
    CreatedAt time.Time
}
```

**领域规则**：
- `IsValid()`：关键词必须有 ID、TenantID、BrandID、Term

**搜索意图分类**：
- `informational`：信息查询（"装修公司怎么选"）
- `transactional`：交易意图（"装修公司报价"）
- `local`：本地意图（"望京附近装修公司"）

### 2.4 MonitoringResult（监测结果实体）

**业务定位**：GEO 最有价值的数据资产，AI 引擎探测的快照

```go
type MonitoringResult struct {
    ID                 string
    TenantID           string
    BrandID            string
    KeywordID          string
    EngineName         string    // 探测的 AI 引擎
    SampleCount        int       // 采样次数
    MentionCount       int       // 提到品牌的次数
    MentionRate        float64   // 提及率 = MentionCount/SampleCount
    AvgPosition        int       // 平均排名（1=最靠前，0=未被提及）
    Sentiment          string    // positive/neutral/negative
    Competitors        []string  // 同次回答里提到的竞品
    CompetitorRates    map[string]float64  // 竞品提及率
    CompetitorSentiments map[string]string // 竞品情感
    CandidateCompetitors []string // AI 回答中自然出现的其他品牌
    Confidence         float64   // 置信度
    ProbedAt           time.Time
    RawSample          string    // 原始回答摘录
    Sources            []string  // 回答中提到的来源
    SelfSourceCount    int       // 来源中包含自营公开站域名的次数
    FirstPickCount     int       // 被提及且位次=1 的采样数
}
```

**设计要点**：
- **采样降噪**：AI 回答有随机性，单次不可信，一次监测对同一引擎采样多次
- **提及率**：用 MentionRate（提及率）而非布尔值，更准确反映品牌可见度
- **竞品对比**：CompetitorRates 提供坐标系（"我 45% vs 竞品 80%"）
- **归因生命线**：Sources 和 SelfSourceCount 区分"提到品牌"和"引用我们的内容"

### 2.5 GenerationTask（生成任务实体）

**业务定位**：统一生成用例的核心资产，所有端点共享的任务模型

```go
type GenerationTask struct {
    ID             string
    TenantID       string
    BrandID        string
    Type           string    // video/image/audio/digital_human/other
    SubType        string    // 17 端点枚举
    Model          string    // viduq3-pro/audio1.0/...
    Provider       string    // vidu/mock
    ProviderTaskID string    // 服务商侧任务 ID
    State          string    // TaskState*
    ErrCode        string    // 服务商错误码
    ErrMsg         string    // 翻译后的产品级消息
    ParamsJSON     string    // 完整提交参数
    Payload        string    // 透传给服务商的本地关联键
    CreationsJSON  string    // 生成物列表
    Credits        int       // 本次消耗积分
    OffPeak        bool      // 错峰模式
    Watermark      bool      // 是否加水印
    CallbackReceived bool    // 回调是否已到达
    CallbackAt     *time.Time
    RetryCount     int       // 自动重试次数
    ParamsHash     string    // 提交参数哈希（防重复提交）
    CreatedAt      time.Time
    UpdatedAt      time.Time
    FinishedAt     *time.Time
}
```

**状态机**：
```
created → queueing → processing → success/failed/cancelled
```

**设计要点**：
- **统一协议**：17 个端点的差异收敛到 SubType + Model + ParamsJSON
- **双通道结果获取**：CallbackReceived 标记回调是否到达，轮询作为兜底
- **幂等性**：ParamsHash 防止重复提交

### 2.6 User（用户实体）

**业务定位**：系统认证和多租户隔离的基础

```go
type User struct {
    ID           string
    Username     string
    PasswordHash string    // 已哈希的密码，绝不存明文
    Role         string    // 角色：admin/merchant
    TenantID     string    // 归属租户 ID
    CreatedAt    time.Time
}
```

**领域规则**：
- `IsValid()`：用户必须有用户名和密码哈希
- `IsAdmin()`：判断是否为管理员
- `IsMerchant()`：判断是否为商户
- `EffectiveTenantID()`：admin 不带 tenant_id 过滤（看全局），merchant 必须用自己的

**多租户设计**：
- 每个用户归属一个 TenantID（商户隔离的根）
- Role 决定权限：admin 看全局，merchant 只看自己的 tenant_id
- admin 的 TenantID 可为空（平台级账号）

### 2.7 Plan（套餐实体）

**业务定位**：SaaS 经济系统的核心，可管理、可热更新的套餐定义

```go
type Plan struct {
    ID         string         `json:"id"`
    Name       string         `json:"name"`
    Level      string         `json:"level"`       // free/pro/team
    PriceCents int            `json:"price_cents"` // 月费（分）
    Quotas     map[string]int `json:"quotas"`      // 场景→当月配额
    Features   []string       `json:"features"`    // 功能白名单
    Status     string         `json:"status"`      // active/archived
    SortOrder  int            `json:"sort_order"`
    CreatedAt  time.Time      `json:"created_at"`
    UpdatedAt  time.Time      `json:"updated_at"`
}
```

**领域规则**：
- `QuotaFor(scene)`：取某场景配额，未配置返回 0（不允许使用）
- `HasFeature(feature)`：判断套餐是否含某功能（功能门禁用）

**设计要点**：
- **配置化**：入库可管理，运营改价/调配额无需发版
- **推迟决策**：把会变的定价策略放数据，不放代码
- **价格用分**：PriceCents int 避免浮点误差（财务系统铁律）

## 3. 值对象分析

### 3.1 TaskStatus（任务状态值对象）

**位置**：`internal/domain/valueobject/task_status.go`

```go
// 生成任务状态（统一状态机）
const (
    TaskStateCreated    = "created"
    TaskStateQueueing   = "queueing"
    TaskStateProcessing = "processing"
    TaskStateSuccess    = "success"
    TaskStateFailed     = "failed"
    TaskStateCancelled  = "cancelled"
)

// IsTerminal 终态判断
func IsTerminal(state string) bool {
    return state == TaskStateSuccess || state == TaskStateFailed || state == TaskStateCancelled
}
```

**设计要点**：
- 终态后回调/轮询重复到达直接忽略——双通道幂等
- 状态机转换由用例层控制，值对象只定义状态和判断规则

### 3.2 ModelCapability（模型能力向量）

**业务定位**：类型化约束，替代裸 JSON schema

```go
type ModelCapability struct {
    Model            string   `json:"model"`
    Family           string   `json:"family"`
    Endpoint         string   `json:"endpoint,omitempty"`
    Durations        [2]int   `json:"durations"`      // 时长范围 [min,max]
    Resolutions      []string `json:"resolutions"`
    AspectRatios     []string `json:"aspect_ratios"`
    AudioDefault     bool     `json:"audio_default"`
    AudioTypes       []string `json:"audio_types"`
    ImageSlots       int      `json:"image_slots"`    // 图片槽位：0/1/2/-1
    VideoSlots       int      `json:"video_slots"`
    SupportsBGM      bool     `json:"supports_bgm"`
    SupportsSubjects bool     `json:"supports_subjects"`
    SupportsMovement bool     `json:"supports_movement"`
    MaxPromptLen     int      `json:"max_prompt_len"`

```

**设计要点**：
- 参数约束按"模型能力"组织而非"参数平铺"
- 校验是直查（duration ∈ [Durations]）而非解释执行配置
- 数据库驱动：generation_specs 表为唯一事实源

## 7. 设计模式在领域层的应用

### 7.1 聚合根模式（Aggregate Root）

- `Brand` 是 GEO 业务的聚合根
- `GenerationTask` 是生成业务的聚合根
- 所有关联实体通过聚合根访问

### 7.2 值对象模式（Value Object）

- `ModelCapability`：模型能力向量
- `CreationItem`：生成物信息
- `PromptRef`：提示词引用

### 7.3 规约模式（Specification）

- `IsValid()`：实体有效性验证
- `IsTerminal()`：终态判断
- `IsActive()`：订阅有效性判断

## 9. 总结

领域层的设计体现了整洁架构的核心思想：

1. **零依赖**：不依赖任何外部框架，纯 Go 代码
2. **业务规则内聚**：验证逻辑、状态判断、领域计算都在实体内部
3. **接口抽象**：通过 Port 接口定义外部依赖，支持 Mock 测试
4. **可测试性**：纯函数和值对象易于单测
5. **可维护性**：业务规则变化只影响领域层，不波及外部
