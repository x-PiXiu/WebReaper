# 搜索引擎收录通知与验证——技术设计文档

> **范围**：内容发布后通知搜索引擎收录（IndexNow / 百度推送）+ 收录状态验证（Bing Webmaster API）
> **架构定位**：adapter 层（收录协议实现）+ usecase 层（编排触发）+ scheduledtask（定时验证）
> **整洁架构**：用例层只依赖 `port.URLSubmitter` + `port.IndexStatusChecker` 接口，协议细节封在 adapter

---

## 一、整体架构：收录闭环

```
内容发布为 published（ContentUseCase.SetStatus / AdminSetStatus）
      │
      ├─ ① 写入 IndexStatus = "pending"（初始状态：已提交未收录）
      │
      └─ ② 触发收录通知（urlSubmitter.SubmitURLs）
              │
              ├─ IndexNow（通知 Bing / Yandex / Naver）
              │     POST https://api.indexnow.org/indexnow
              │
              ├─ 百度主动推送（通知百度爬虫）
              │     POST http://data.zz.baidu.com/urls?site=xxx&token=xxx
              │
              └─ Bing URL Submission（向 Bing 请求编制索引，100 条/天配额）
                    POST https://ssl.bing.com/webmaster/api.svc/json/SubmitUrlBatch
                        │
                        │  ...数小时~数天后搜索引擎爬取并收录...
                        │
                        ↓
      ③ 定时验证任务（IndexCheckTask，每 24h）
              │
              ├─ 查所有 status=published 且 IndexStatus≠indexed 的内容
              │
              ├─ 调 Bing Webmaster API 逐条查询收录状态
              │     GET https://ssl.bing.com/webmaster/api.svc/json/GetUrlInfo
              │
              └─ 回写 IndexStatus：
                    indexed（已收录）→ 记录 IndexedAt 时间
                    pending（未收录）→ 保持等待
                    error（查询失败）→ 不改写，下次重试
```

**核心设计思想**：通知 ≠ 收录。IndexNow 只保证"已通知"，是否真正收录需要二次验证。两条链路构成完整闭环。

### 2.3 IndexNow 实现

**代码位置**：`internal/adapter/indexnow/indexnow.go`

#### 协议说明

IndexNow（https://www.indexnow.org）是一个免费开放的协议，支持 **Bing / Yandex / Naver** 等搜索引擎。提交后新页面在数小时~数天内被收录。

#### 请求格式

```
POST https://api.indexnow.org/indexnow
Content-Type: application/json

{
  "host": "content.example.com",
  "key": "a1b2c3d4e5f6g7h8",
  "keyLocation": "https://content.example.com/public/indexnow-key.txt",
  "urlList": [
    "https://content.example.com/public/articles/oc-123"
  ]
}
```

#### 密钥验证机制

IndexNow 协议要求：
1. 生成一个 8-128 位的十六进制密钥（格式：`[a-zA-Z0-9-]`）
2. 在站点根目录托管一个纯文本文件，内容就是密钥本身
3. 每次提交时带上 `keyLocation` 指向这个文件——搜索引擎会访问它校验密钥有效性

**项目实现**：密钥文件由公开站端点 `/public/indexnow-key.txt` 托管（`public_handler.go`）。
- 同时兼容 IndexNow 协议要求的 `/{key}.txt` 路径（Gin 动态路由 `/:key.txt`）
- 密钥通过 `.env` 的 `INDEXNOW_KEY` 配置，admin 后台收录管理页可自动生成

#### 响应状态码

| HTTP 状态码 | 含义 |
|---|---|
| 200 | 提交成功，搜索引擎已接受 |
| 202 | 提交已接受，稍后处理 |
| 422 | 密钥格式无效或 keyLocation 无法访问 |
| 422 | URL 与 host 不匹配 |
| 其他 4xx/5xx | 提交失败 |

### 2.4 百度主动推送实现

**代码位置**：`internal/adapter/urlsubmit/baidu.go`

#### 协议说明

百度站长平台的主动推送 API，用于通知百度爬虫收录新页面。

#### 请求格式

```
POST http://data.zz.baidu.com/urls?site=content.example.com&token=xxx
Content-Type: text/plain

https://content.example.com/public/articles/oc-123
https://content.example.com/public/articles/oc-456
```

- 每行一个 URL（text/plain，不是 JSON）
- 单次最多 2000 条（代码自动分片）
- 每日配额约 10 万条（与手动提交共享）

#### 响应

```json
{
  "remain": 99998,
  "success": 2,
  "not_same_site": [],
  "not_valid": []
}
```

- `remain`：当日剩余配额
- `success`：成功提交数
- `not_same_site`：与站点不匹配的 URL
- `not_valid`：无效 URL

#### 配置

| 配置项 | 来源 | 说明 |
|---|---|---|
| `BAIDU_SITE` | `.env`（百度站长平台） | 已验证域名 |
| `BAIDU_TOKEN` | `.env`（百度站长平台 → 资源提交 → API 推送） | 准入 token |

### 2.5 Bing URL Submission API 实现

**代码位置**：`internal/adapter/urlsubmit/bing.go`

#### 协议说明

Bing Webmaster Tools 后台的"URL 提交/请求编制索引"（每日约 100 次机会）**有官方 API**，
与后台手动提交**共享同一配额**。实测配额接口：

```json
{"d":{"__type":"UrlSubmissionQuota:#Microsoft.Bing.Webmaster.Api","DailyQuota":100,"MonthlyQuota":1800}}
```

#### 请求格式

```
POST https://ssl.bing.com/webmaster/api.svc/json/SubmitUrlBatch?apikey={key}
Content-Type: application/json

{
  "siteUrl": "https://content.example.com",
  "urlList": [
    "https://content.example.com/public/articles/oc-123",
    "https://content.example.com/public/articles/oc-456"
  ]
}
```

- 单次最多 100 条（代码自动分片）
- `apikey` 走查询参数；与收录验证（GetUrlInfo）**共用同一把 key**——无需新增配置项
- 相关端点：
  - `POST .../SubmitUrl`：单条提交
  - `GET .../GetUrlSubmissionQuota?siteUrl=...&apikey=...`：查询剩余配额

#### 响应语义

| HTTP 状态码 | 含义 |
|---|---|
| 200 | 已受理，URL 进入 Bing 爬取队列 |
| 429 | 配额用尽（与后台手动提交共享 100 条/天） |
| 其他 4xx/5xx | 提交失败 |

> ⚠️ **200 ≠ 已收录**——提交只是进入爬取队列，是否进入索引由 Bing 按内容质量决定
> （官方原文："Bing does not guarantee that all content submitted will be indexed"）。

#### 配置与装配

- 复用 `BING_API_KEY` / `BING_SITE_URL`（env，重启生效；`cmd/server/main.go` 装配）
- 已配置时作为**兜底渠道**挂入 `MultiSubmitter`：`CachedProvider（IndexNow/百度）⊕ BingSubmitter`
- 未配置则仅走 IndexNow/百度，行为与旧版完全一致

#### 定位：IndexNow 的兜底渠道

| | IndexNow（主渠道） | Bing URL Submission（兜底） |
|---|---|---|
| 覆盖 | Bing / Yandex / Naver / Seznam | 仅 Bing |
| 配额 | 无限（有速率限制） | 100 条/天（与后台共享） |
| 验证机制 | 域名托管 key 文件 | Bing 账号 API key |
| 收录速度 | 快（Bing 高优先级重新排队） | 一般 |
| 语义 | 通知"有 URL 新增/变更" | 请求"编制索引" |

**语义澄清**：两者本质都是"**通知/请求**"，都不是"保证收录"——提交后是否进入索引，
都由搜索引擎按**内容质量**决定。URL Submission 的后台文案叫"请求编制索引"，容易误解为
"直接申请收录"，实际同样只是**进入爬取队列的优先级信号**，与 IndexNow 是同一层语义，
区别在覆盖面、配额和验证方式。接入价值在于：IndexNow 偶发延迟/未生效时多一个提交通道
（双通道提交已由实测验证不冲突）。

### 2.6 多通道组合（MultiSubmitter）

**代码位置**：`internal/adapter/urlsubmit/multi.go`

使用组合模式，并行向所有已配置的渠道提交，失败互不影响：

```go
type MultiSubmitter struct {
    submitters []port.URLSubmitter
}
```

- 并行提交（goroutine + WaitGroup）
- 任一渠道失败不影响其他渠道
- 全部成功返回 nil；任一失败返回聚合错误（errors.Join）

### 2.7 动态配置（CachedProvider）

**代码位置**：`internal/adapter/urlsubmit/cached.go`

支持运行时配置免重启——管理后台改了 IndexNow key 或百度 token 后，30 秒内自动生效：

```go
type CachedProvider struct {
    load     ConfigLoader               // 从 system_settings 加载配置
    ttl      time.Duration              // 30 秒缓存
    cached   port.URLSubmitter          // 缓存的 MultiSubmitter 实例
}
```

- 每次提交时检查缓存：TTL 30 秒内复用已构建的 MultiSubmitter
- 过期则从 ConfigLoader 重新读取并按配置重建（新增/移除渠道自动生效）
- 未配置任何渠道时返回 no-op（提交空转成功，不阻断业务）

### 3.2 Bing Webmaster API 实现

**代码位置**：`internal/adapter/bing/checker.go`

#### API 端点

```
GET https://ssl.bing.com/webmaster/api.svc/json/GetUrlInfo
    ?apikey={BING_API_KEY}        ← Bing 站长 API 密钥
    &siteUrl={BING_SITE_URL}      ← 已验证站点地址
    &url={文章 URL}               ← 如 https://content.example.com/public/articles/oc-123
```

> **迁移记录（2026-08-14）**：早期实现使用 `GetUrlSubmissionStatus` 端点，实测该端点在
> 公开 API 中不存在（返回 HTML "Endpoint not found"），导致所有查询恒为 error——收录
> 验证形同虚设。已迁移至 `GetUrlInfo`，并基于真实响应样本重写解析与测试。

#### 响应格式

`GetUrlInfo` 返回 JSON，两种形态：

**正常（UrlInfo 对象）**：

```json
{
  "d": {
    "__type": "UrlInfo:#Microsoft.Bing.Webmaster.Api",
    "DiscoveryDate": "/Date(1786604400000-0700)/",
    "DocumentSize": 0,
    "HttpStatus": 0,
    "IsPage": true,
    "LastCrawledDate": "/Date(1786626352000)/",
    "TotalChildUrlCount": 0,
    "Url": "https://content.example.com/public/articles/oc-123"
  }
}
```

**API 错误**（不是字符串 `"Error"`，而是带错误码的对象）：

```json
{ "ErrorCode": 3, "Message": "ERROR!!! InvalidApiKey" }
```

#### .NET 日期格式（关键陷阱）

`DiscoveryDate` / `LastCrawledDate` 是 .NET JSON 日期：`/Date(毫秒[±时区])/`。

⚠️ **从未抓取的 URL，其 `LastCrawledDate` 不是空值，而是 .NET `DateTime.MinValue`
（`/Date(-62135568000000-0800)/`，即 0001-01-01）**——判断"是否抓取"必须校验毫秒为正数，
不能只看字段是否为空。

#### 响应解析（状态映射）

| 响应形态 | 解析结果 | 含义 |
|---|---|---|
| `ErrorCode ≠ 0`（如 InvalidApiKey） | `"error"` | API 错误：密钥无效 / 限流 / 站点未验证 |
| `{"d": null}` | `"pending"` | Bing 从未发现该 URL |
| `LastCrawledDate` 有效（正毫秒） | `"indexed"` | 已被 Bing 抓取（公开 API 可拿到的最强收录信号） |
| `LastCrawledDate` 为 MinValue | `"pending"` | 已发现但从未抓取 |
| 非 JSON（HTML 错误页等） | `"error"` | 解析失败 |

#### 解析代码

```go
func (c *Checker) parseBody(body []byte) string {
	var resp urlInfoResponse
	if err := json.Unmarshal(body, &resp); err != nil {
		return "error"
	}
	if resp.ErrorCode != 0 {
		return "error"
	}
	if resp.D == nil {
		return "pending"
	}
	if dotnetMillis(resp.D.LastCrawledDate) > 0 {
		return "indexed"
	}
	return "pending"
}
```

#### 设计要点（整洁架构）

- **传输与解析分离（单一职责）**：`checkOne` 只负责传输（URL 拼接 / 超时 / 非 200 判定），
  `parseBody` 是纯函数只做解析——解析逻辑可脱离 HTTP 独立单测
- **显式响应契约**：用 `urlInfoResponse` / `urlInfo` struct 描述响应，替代 `any` 类型体操——
  弱类型解析会在 API 变更时悄悄错判（本次 bug 的根源之一）
- **状态语义内聚在 adapter**：usecase / 定时任务只认 `indexed` / `pending` / `error` 三态，
  协议细节（.NET 日期、错误码）不泄漏到上层

#### 查询方式

- **串行逐条查询**（非批量）——Bing API 不支持批量查询
- 每条 HTTP 请求超时 10 秒
- 非 200 响应 / 单条失败不阻断其余（标记为 error，下次重试）

### 3.3 定时验证任务

**代码位置**：`internal/adapter/scheduledtask/tasks_index.go`

#### 任务参数

| 属性 | 值 |
|---|---|
| 任务名 | `index-status-check` |
| 执行间隔 | 24 小时 |
| 分布式锁 | `NoopLock`（单机）/ `RedisLock`（多实例） |
| 前置条件 | `BING_API_KEY` + `BING_SITE_URL` 已配置（否则空转） |

#### 执行逻辑

```
1. 检查 checker 是否为 nil → 空转退出（未配置 Bing 凭据）
2. 查所有已发布内容（ListPublished）
3. 过滤：跳过 IndexStatus == "indexed" 的（已确认收录，节省 API 配额）
4. 拼公开站 URL：{PUBLIC_BASE_URL}/public/articles/{contentID}
5. 调 checker.CheckURLs(urls) 逐条查 Bing
6. 回写：
   - indexed → UpdateIndexStatus(indexed, now)  记录收录时间
   - pending → UpdateIndexStatus(pending, zero)  保持等待
   - error   → 不改写（下次重试）
7. 日志输出统计：checked / indexed / pending / failed
```

#### 内容状态流转

```
发布时（ContentUseCase.SetStatus）
  → IndexStatus = "pending"（初始）

定时验证（IndexCheckTask）
  → Bing 查询结果：
     indexed → IndexStatus = "indexed" + IndexedAt = now
     pending → IndexStatus = "pending"（不变）
     error   → 不改写（下次重试）
```

### 3.4 实测记录（2026-08-14）

> 使用生产环境 API key 对 `https://geo.zhichen.chat/` 实测，验证端点可用性与状态语义。

| 验证项 | 请求 | 响应 | 结论 |
|---|---|---|---|
| 端点可用性 | `GetUrlInfo?apikey=<真实key>&siteUrl=https://geo.zhichen.chat&url=<文章URL>` | `{"d":{UrlInfo...}}` | ✅ API key 有效、`BING_SITE_URL` 传 `https://geo.zhichen.chat`（尾斜杠可省） |
| 已抓取文章 | `oc-1786626290004634303` | `DiscoveryDate=2026-08-13 15:00 UTC`，`LastCrawledDate=2026-08-13 21:05 UTC`，`IsPage=true` | ✅ 已发现并抓取 → 判定 `indexed` |
| 未收录 URL | 不存在的文章 ID | `LastCrawledDate=/Date(-62135568000000-0800)/`（.NET MinValue） | ✅ 判定 `pending`（关键：MinValue 而非空值） |
| 错误密钥 | `apikey=wrongkey` | `{"ErrorCode":3,"Message":"ERROR!!! InvalidApiKey"}` | ✅ 判定 `error` |

Bing 已完成"发现+抓取"，但尚未进入可搜索的索引。GetUrlInfo 的 `LastCrawledDate`
是公开 API 能拿到的最强收录信号，无法再进一步（Bing 不公开索引位次数据）。

### 4.3 Bing API Key 获取步骤

> 官方文档：https://learn.microsoft.com/en-us/bingwebmaster/getting-access

1. 登录 [Bing Webmaster Tools](https://www.bing.com/webmasters)
2. 添加并验证站点（`BING_SITE_URL` 对应的域名）
   - Meta 标签验证：首页 `<head>` 加 `<meta name="msvalidate.1" content="{验证码}" />`
   - XML 文件验证：根目录放 `BingSiteAuth.xml`
   - CNAME 验证：加 DNS 记录
3. Settings → API Access → API Key → Generate API Key
4. 复制 API Key，填入 `.env` 的 `BING_API_KEY`

**注意**：
- 一个 Bing 账号只有一个 API Key，可用于该账号下所有已验证站点
- 该 Key 同时用于：① Bing URL Submission（提交，100 条/天配额，与后台"URL 提交"共享）② GetUrlInfo（收录状态验证）
- 配额查询：`GET https://ssl.bing.com/webmaster/api.svc/json/GetUrlSubmissionQuota?siteUrl={site}&apikey={key}`

### 4.4 百度 Token 获取步骤

1. 登录 [百度搜索资源平台](https://ziyuan.baidu.com/)
2. 添加并验证站点
3. 普通收录 → 资源提交 → API 推送
4. 复制准入 token，填入 `.env` 的 `BAIDU_TOKEN`

## 六、设计原则（整洁架构）

### 6.1 依赖倒置

```
ContentUseCase → port.URLSubmitter（接口）
                     ↑ 实现
        ┌─────────────────┼─────────────────┐
  indexnow.Submitter  baidu.Submitter  BingSubmitter  MultiSubmitter  CachedProvider
```

新增收录渠道（如 Google Indexing API）= 新 adapter 实现 + main 装配，usecase 零改动。
本次 Bing URL Submission 接入即按此模式：新增 `urlsubmit/bing.go` + main 装配，usecase 零改动。

### 6.2 开闭原则

- CachedProvider 内部按配置动态构建 MultiSubmitter —— admin 后台开关某个渠道，30 秒内生效，不重启
- IndexCheckTask 的 checker 参数是接口 —— 未来接 Google Search Console API 只需新 adapter

### 6.3 尽力而为语义

收录通知（SubmitURLs）和收录验证（CheckURLs）都是"尽力而为"：
- 通知失败：`_ = uc.urlSubmitter.SubmitURLs(...)` 忽略错误，不阻断发布
- 验证失败：单条标记 error，不阻断其余条目，下次重试
- 未配置：空转（nil 安全），不影响主业务

### 6.4 失败隔离

MultiSubmitter 并行提交多渠道，任一渠道失败不影响其他渠道。一条 URL 即使百度推送失败，IndexNow 仍能成功通知 Bing。
