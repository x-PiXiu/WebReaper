> 📌 WebReaper 从"数据采集工具"向"多商户 GEO SaaS 平台"演进的战略规划。

## ⭐ 核心结论速览

1. **方向反转但资产可复用**：WebReaper 是"把数据拉进来"（采集），GEO 是"把内容推出去并被 AI 引用"。LLM/Agent/向量/分发四件套约 50% 可直接复用，是转型的最大优势。

2. **GEO 的本质是闭环，不是工具堆砌**：监测（现状）→ 诊断（问题）→ 优化（改进）→ 分发（投放）→ 再监测（验证）。所有功能围绕 `Brand`/`Keyword`/`MonitoringResult` 组织，而不是围绕 `Crawler`/`LLM`/`Publisher` 这些技术细节。

3. **可行性边界明确**：多租户、AI 监测、内容生成、GEO 评分 = 🟢 完全可行；知乎/抖音发布 = 🟡 脆弱可行（需持续对抗风控）；全自动无人值守发布 = 🔴 长期不可行（平台不开放）。

4. **三个必须纠正的认知**：① "自动获取 cookie"做不到（只能扫码绑定+复用）；② "浏览器黑盒运行"是灰盒（需反检测对抗）；③ "一个商户一个 cookie"要改为账号池（单号高频必封）。

5. **商户端 = 同一套系统的商户视图**：多一个 merchant 角色和受限 API，不是独立 App。核心业务代码零重复，靠 JWT 里的 `tenant_id` 隔离。

6. **发布层是脆弱但可隔离的增值功能**：用 `PublishChannel` 接口把各平台差异关在最外层适配器。混合策略——有 API 的平台全自动（公众号/微博），没 API 的平台半自动（知乎/小红书），最后才碰抖音全自动。

7. **落地按稳定性排序**：先做监测（最稳、能收费）→ 再做生成 → 再做半自动发布 → 最后做脆弱的 RPA 和视频。先把闭环的"眼睛"做扎实，再做"手脚"。
