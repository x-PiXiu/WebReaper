# GEO 演进战略与可行性分析

> 📌 WebReaper 是"把数据拉进来"（采集），GEO 是"把内容推出去并被 AI 引用"。方向相反，但 LLM/Agent/向量/分发四件套可直接复用。本文基于《整洁架构之道》分析转型的能力复用、能力缺口与可行性边界。

## 一、战略转向：从采集工具到 GEO SaaS

### 1.1 为什么转向 GEO

WebReaper 当前的业务闭环是"采集 → AI 加工 → 多平台推送"，本质是**内容生产工厂**。GEO（Generative Engine Optimization，生成式引擎优化）的业务目标是"让品牌内容被 AI 引擎优先引用"——这是一个**更高价值、更适合 SaaS 化**的方向：

| 维度 | WebReaper 现状（采集） | GEO 转型后 |
|---|---|---|
| 业务方向 | 把外部数据拉进来 | 把品牌内容推出去并优化其 AI 可见度 |
| 付费方 | 工具使用者（按需） | 商户（按月订阅，SaaS）|
| 价值锚点 | 省人工 | 提升 AI 搜索排名（直接关联获客）|
| 数据资产 | 采集到的数据 | 品牌的 AI 可见度历史趋势 |

### 1.2 核心论点

> **GEO 的本质业务规则**（实体层，去掉所有软件也成立）：让某品牌的内容，在用户向 AI 引擎提问时，被 AI 理解、信任、优先引用。

这条规则决定了系统不是工具堆砌，而是一个**闭环**：

```
监测（现状）→ 诊断（问题）→ 优化（改进）→ 分发（投放）→ 再监测（验证）
   ↑                                                              │
   └──────────────────────── 闭环反馈 ─────────────────────────────┘
```

整洁架构 § 三"尖叫的架构"要求：**好的架构让人一眼看出系统是干嘛的**。GEO 系统的目录应该围绕 `Brand`/`Keyword`/`MonitoringResult` 组织，而不是围绕 `Crawler`/`LLM`/`Publisher` 这些技术细节组织。

## 二、能力复用地图（对照真实代码）

WebReaper 已有的基础设施中，约 **50% 可直接复用**，这是转型的最大优势：

| GEO 需要的能力 | WebReaper 现状 | 复用度 | 说明 |
|---|---|---|---|
| LLM / Agent 调用 | `port.AIGenerator` + `TrpcAgentGenerator` + `AgentConfig`（可动态切模型） | ⭐⭐⭐⭐ 直接复用 | GEO 监测多家 AI 引擎的基础 |
| 多模型并行调用 | 已支持多 `LLMConfig`（MiniMax/DeepSeek/智谱…） | ⭐⭐⭐⭐ 直接复用 | 同时监测豆包/文心/Kimi |
| 内容存储 | `DataItem`（title/content/summary/tags/status） | ⭐⭐⭐ 复用扩展 | 需加 GEO 评分等字段 |
| 向量检索 | `vectorstore` + `embedding` | ⭐⭐⭐ 复用 | 内容相似度/语义去重 |
| 多平台分发 | `external_system` 推送（raw/mapping 双模式） | ⭐⭐⭐ 框架复用 | 语义要从"推数据"改为"发内容" |
| 图编排 | `graph_orchestrator`（探查→生成→校验） | ⭐⭐⭐ 框架复用 | 节点语义重写为 GEO 流程 |
| 数据看板 | `Dashboard` + `StatsUseCase` | ⭐⭐ 框架复用 | 指标换为 GEO 指标 |
| 会话/任务管理 | `Conversation` / `Task` 子系统 | ⭐⭐⭐ 复用 | 监测任务调度 |
| 多 LLM 切换 | 聊天界面动态切 LLM（已实现） | ⭐⭐⭐⭐ 直接复用 | 多引擎监测的 UI 基础 |

## 三、能力缺口：必须新增的三大领域

WebReaper 缺的不是基础设施，是 **GEO 的业务领域模型**。三块完全空白：

### 3.1 AI 引擎监测层（最关键的新能力）

**实体规则**（最内层，不依赖软件）：
- "同一个问题问豆包/文心/Kimi/DeepSeek，回答不同，且每次可能变化"
- "AI 回答中的品牌提及位置、次数、上下文，反映该品牌的'被引用能力'"

> ⚠️ **监测可信度是 GEO 的生死线**：AI 回答有随机性，必须**多次采样 + 统计**（如问 5 次取提及率），不能问一次就当结论。这是实体层的业务规则，漏掉则整个产品的可信度坍塌。

技术实现：这其实不是"爬虫"，是"批量调用 LLM"。可新增一个实现 `crawler.Tool` 接口的 `AIEngineProbe` 适配器——它实现工具接口，但内部是调 `LLMConfig` 问问题 + 解析回答。现有的 `ToolRegistry` 注册机制零改动就能挂上去。

### 3.2 GEO 评分模型（核心领域逻辑）

**实体规则**：
- "内容能否被 AI 引用，取决于权威性、具体性、结构化程度、独特性、时效性"
- "评分逻辑与具体 AI 引擎无关——这是内容本身的属性"

实现：纯函数 `GEOScore(content, keyword) → Score`，最内层零框架依赖。WebReaper 的 `domain/entity` 目前是纯 struct，加这个评分逻辑很自然。

### 3.3 品牌/关键词资产域（全新的聚合根）

WebReaper 围绕 `Task → DataItem → Collection`（采集心智）组织。GEO 应围绕 **`Brand → Keyword → MonitoringResult → OptimizedContent`** 组织：

```
采集心智（现状）              GEO 心智（目标）
Task（采集任务）       →     MonitoringJob（监测任务）
DataItem（采集结果）   →     MonitoringResult + OptimizedContent
Collection（采集集合） →     Brand（品牌资产聚合根）
AgentConfig（采集助手）→     优化Agent / 监测Agent（框架同，提示词不同）
```

**不破坏现有架构**——`AgentConfig`/`LLMConfig`/`Conversation`/`DataItem` 基础设施实体原封不动，在其上叠加 GEO 领域实体。

## 四、可行性判定（红/黄/绿）

下死判断，不模糊：

| 功能 | 可行性 | 核心技术 | 难点 / 风险 |
|---|---|---|---|
| 多租户隔离 | 🟢 完全可行 | DB 层 `tenant_id` + 中间件注入 + 仓储强制过滤 | 越权是 SaaS 致命伤，需安全审计 |
| AI 关键词监测/排行榜 | 🟢 完全可行 | 调多家 LLM API + 解析品牌提及 + 多次采样统计 | 采样降噪，统计取值而非单次 |
| 品牌内容生成 | 🟢 完全可行 | LLM + 品牌定位提示词 + 图编排校验 | 内容质量决定客户留存 |
| GEO 评分与诊断 | 🟢 完全可行 | 评分纯函数 + 诊断 Agent | 评分与实际引用的相关性需校准 |
| 账号绑定（扫码） | 🟢 可行 | Playwright 渲染登录页 + 抓 cookie + 加密存库 | cookie 会过期，要续期/重扫机制 |
| 账号池调度 | 🟢 可行 | 轮询/权重调度 + 健康检查 + 封号检测 | 单账号高频必封，必须多号轮换 |
| 知乎/小红书发布 | 🟡 脆弱可行 | Playwright + stealth + cookie 复用 | 平台风控随时变，需持续维护 |
| 抖音视频发布 | 🟡 脆弱可行 | Playwright + 大文件分片 + 设备指纹 | 抖音风控最强，封号风险最高 |
| 全自动无人值守发布 | 🔴 长期不可行 | —— | 平台不开放，强做=对抗平台=随时被封 |

## 五、三个必须纠正的认知错误

转型前必须对齐认知，否则会导致架构设计建立在错误前提上：

### 错误 1：「自动获取 cookie 登录知乎」——做不到

知乎/抖音/小红书**没有账号密码登录 API**，登录方式是**扫码或短信验证码**，这俩都需要真人操作。正确做法是**一次性扫码绑定 + cookie 复用**：商户首次扫码（真人）→ 拿到 cookie → 加密存库 → 后续发布复用 → 过期通知重新扫码。

### 错误 2：「浏览器黑盒运行」——是"灰盒"，不是黑盒

Playwright 能跑无头浏览器，但平台**主动检测**无头（`navigator.webdriver`、浏览器指纹、鼠标轨迹）。能用 stealth 插件伪装，但这是**猫鼠游戏**——平台升级风控，伪装要跟着改。正确态度：把这层当"最易变的外部细节"用边界彻底隔离（整洁架构 § 7.6C 推迟决策清单）。

### 错误 3：「一个商户一个 cookie」——要的是账号池

单账号高频发布必封。矩阵号运营的真相是**一个商户多个账号轮换发布**。要建模的不是"账号"，而是**"账号池 + 发布调度策略"**。

## 六、架构分层落点（整洁架构视角）

```
┌─────────────────────────────────────────────────────────────┐
│ 框架与驱动层（最易变，可替换）                                  │
│   · Playwright/Chromium（无头浏览器，发布用）         ⚠️脆弱  │
│   · 各 AI 引擎 SDK（豆包/文心/Kimi/DeepSeek）         ✅稳定  │
│   · MySQL + Redis + 对象存储（视频/图片）             ✅稳定  │
│   · stealth 反检测插件                               ⚠️需维护 │
│  ┌───────────────────────────────────────────────────────┐ │
│  │ 接口适配器层                                            │ │
│  │   · AIEngineProbe（问 LLM、解析品牌提及）      ✅新增   │ │
│  │   · ZhihuPublishChannel（Playwright 发布）    ⚠️新增   │ │
│  │   · BrowserPool（无头浏览器生命周期管理）      ⚠️新增   │ │
│  │   · CookieVault（cookie 加密存储）            ✅新增   │ │
│  │   · GORM Repos（多租户隔离的仓储）            ✅复用改进│ │

│  │  │ 用例层（应用级业务规则）                       │     │ │
│  │  │   · MonitorUseCase（AI 关键词监测）   ✅核心  │     │ │
│  │  │   · GenerateContentUseCase（生成文章）✅核心 │     │ │
│  │  │   · PublishUseCase（发布调度）       ⚠️核心  │     │ │
│  │  │   · RankUseCase（排行榜计算）        ✅核心  │     │ │
│  │  │   · AccountPoolUseCase（账号池调度） ✅核心  │     │ │
│  │  │  ┌───────────────────────────────────┐     │     │ │
│  │  │  │ 实体层（企业级业务规则）              │     │     │ │
│  │  │  │   · Tenant（商户）                  │     │     │ │
│  │  │  │   · Brand（品牌资产）               │     │     │ │
│  │  │  │   · Keyword（关键词）               │     │     │ │
│  │  │  │   · Account（平台账号+cookie）      │     │     │ │
│  │  │  │   · MonitoringResult（监测快照）    │     │     │ │

│  │  └─────────────────────────────────────────────┘     │ │

```

**关键纪律**：用例层**绝对不能 import** Playwright、stealth 插件、任何平台 SDK。它只依赖自己声明的 `PublishChannel`/`AIEngineProbe` 接口。浏览器自动化全关在最外层适配器里，哪天失效重写那一个模块，业务零影响。

## 七、多租户与商户端（架构关键决策）

### 7.1 多租户是 SaaS 的生命线

整洁架构里这是**实体层的硬规则**：

- 所有数据查询必须带 `tenant_id` 过滤
- 所有 cookie/凭证按租户加密
- 跨租户访问 = 编程错误，必须在仓储层硬拦
- **单元测试必须覆盖"租户 A 查不到租户 B 数据"**（整洁架构 § 六：测试是架构健康度体检）

技术实现：
- HTTP 中间件从 JWT 解出 `tenant_id`，注入 context
- 仓储层每个查询方法强制 `WHERE tenant_id = ?`
- cookie 用**租户级密钥**加密（KMS 管理，一租户泄露不影响其他）

### 7.2 商户端：是同一套系统的"商户视图"，不是独立 App

商户端和管理端的差异**只在接口适配器的权限层**，不在业务核心：

| 维度 | 管理端（你/运营） | 商户端（客户） |
|---|---|---|
| 能看到的品牌 | 所有租户的 | 只有自己的（租户隔离）|
| 能管理的账号池 | 所有租户的账号 | 只有自己的 |
| 能做的事 | 全局配置、收费、封号 | 建品牌、绑账号、看监测、生成内容 |
| 数据范围 | 跨租户聚合 | 强制 `WHERE tenant_id = ?` |

**架构上的正确做法**：多租户 SaaS 本来就是"同一个后端 + 按 JWT 里的 tenant_id 隔离"。商户端只是**多一个角色（merchant）和一套受限的 API**，不是第二个系统。前端可以是同一个 React 仓库里的一套路由（按角色渲染不同页面），也可以是两个入口共享同一套 API client。**核心业务代码（监测/生成/发布用例）零重复。**

## 八、三个决定成败的隐蔽功能

按重要性排序，这三块不做好，GEO 就是花架子：

### 8.1 监测可信度保障（采样与统计）

同一关键词对同一引擎**多次采样**（3~5 次），统计**提及率**（5 次提到 3 次 = 60%）而非单次布尔值。提供监测的"置信度"指标（采样次数少则置信度低）。归属：实体层业务规则。

### 8.2 竞品基准（Benchmark）

单看自己没意义，要有对比。监测某关键词时同时抓取 AI 回答里的**所有品牌**，维护**行业排名榜**，跟踪**竞品的内容策略**。归属：用例层编排逻辑。这是 GEO 区别于"单纯监测工具"的价值——给客户**相对位置**而非绝对数据。

### 8.3 合规与真实性边界

GEO 的诱惑是"优化内容让 AI 引用"，但越过线就是**造假**。实体层硬规则：禁止生成虚假数据/案例/资质；内容真实性校验（优化后必须能追溯真实事实）；关键词堆砌检测（过度优化会被 AI 降权）；操作审计。**这不是功能选项，是 GEO 产品的合规底线。**

## 九、务实落地顺序（按稳定性从高到低）

> 核心原则：**先做最稳的把现金流跑起来，最后碰最脆弱的。**

| 阶段 | 内容 | 可行性 | 能否收费 | 决策依据 |
|---|---|---|---|---|
| **阶段 1** | 多租户 + AI 关键词监测 + 排行榜 | 🟢 | ✅ 客户为"知道自己在 AI 里排第几"付费 | 监测是闭环起点，验证 GEO 是否成立 |
| **阶段 2** | 品牌内容生成 + GEO 评分 | 🟢 | ✅ 客户为"AI 帮我写优化内容"付费 | 评分与实际引用的相关性需校准 |
| **阶段 3** | 账号扫码绑定 + 知乎半自动发布 | 🟢 | ✅ 客户为"一键准备好待发布内容"付费 | 半自动风险最低，合规优先 |
| **阶段 4** | 浏览器池 + 知乎全自动 RPA 发布 | 🟡 | ⚠️ 客户愿承担封号风险才做 | 验证全自动的真实需求强度 |
| **阶段 5** | 抖音视频生成 + 发布 | 🟡 | ⚠️ 最后做，风险最高 | 文本分发跑通后再碰视频 |

**为什么这么排序**：监测是闭环的起点，也是验证"GEO 这件事是否成立"的最低成本方式。如果阶段 1 的监测数据不可信、客户不认，后面优化和分发做得再花哨也没用。**先把闭环的"眼睛"做扎实，再做"手脚"。**

## 十、技术栈选型

| 层 | 技术 | 理由 |
|---|---|---|
| 后端框架 | Go（复用 WebReaper） | 并发好（浏览器池/任务调度），架构资产复用 |
| 浏览器自动化 | Playwright（首选） | 比 Puppeteer 抗检测能力强，支持多浏览器 |
| 反检测 | playwright-extra + stealth | 伪装无头浏览器指纹 |
| 任务调度 | Redis + 定时器（或 Asynq） | 监测周期跑、发布排队 |
| cookie 加密存储 | KMS + AES-GCM | 租户级密钥隔离 |
| 数据库 | MySQL（复用）或 PostgreSQL | 多租户用行级 `tenant_id` 隔离 |
| 视频生成（后期）| FFmpeg + TTS + 图像合成 | 独立子系统，不与文本发布混 |
| 前端 | React（复用） | 多租户仪表盘，按角色渲染 |

## 十一、关于"全自动发布"的最终结论

> **这个 SaaS 能做出来，核心价值在监测和生成（稳定），发布层是脆弱但可隔离的增值功能。** 用整洁架构的边界把脆弱的发布层关起来，让它哪天失效也不拖垮主业务。

| 问题 | 答案 |
|---|---|
| 多租户 GEO SaaS 可行吗？ | **完全可行，这是对的方向** |
| 商户各有账号池能做吗？ | **能，扫码绑定 + cookie 复用 + 池调度** |
| 自动获取 cookie？ | **不能自动，只能一次性扫码 + 复用续期** |
| 浏览器黑盒运行？ | **能（headless + stealth），但是灰盒、需持续对抗** |
| 全自动无人值守发布？ | **长期不可行，平台不让；半自动 + 部分 API 是务实解** |
| AI 关键词排行榜？ | **完全可行，调 LLM API 即可，是最稳的卖点** |
