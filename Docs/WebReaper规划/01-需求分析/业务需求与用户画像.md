# 业务需求与用户画像

> 📌 本文档从用户的原始需求出发，用五步分析法的"信号提取"环节，把口语化需求翻译为技术实体，并识别目标用户群体。

## 一、原始需求记录

以下是用户在项目演进过程中提出的核心需求原话（按时间顺序）：

| # | 用户原话 | 提出阶段 |
|---|---|---|
| 1 | "使用 go 以及 trpc-agent-go 框架编写一个数据采集系统，前后端 web 形式，需要分多个功能后续还会拓展" | 项目立项 |
| 2 | "比如有爬虫爬取招聘网站的招聘需求，然后根据招聘需求整理出相关的面试题之类的" | 功能举例 |
| 3 | "还有爬取网络中的数据然后清洗总结为知识点等" | 功能举例 |
| 4 | "根据整洁架构设计思想你觉得该如何实现" | 架构要求 |
| 5 | "作为外部系统将数据推送到其他平台...需要设计为接口，便于后续添加其他平台" | 推送需求 |
| 6 | "根据整洁架构设计思想继续推进下一步实现" | 迭代推进 |

## 二、需求信号提取

把用户原话中的"动词"和"名词"翻译为代码角色：

### 动词 → 接口方法

| 用户原话关键词 | 代码中的方法 | 落地的用例 |
|---|---|---|
| 爬取、采集 | `Crawl()` / `Collect()` | `CollectJobPosts` |
| 整理、生成 | `GenerateQuestions()` | `GenerateQuestions` |
| 清洗、总结 | `SummarizeKnowledge()` | `SummarizeKnowledge` |
| 推送 | `Publish()` | `PublishContent` |
| 分发 | `PublishArticle()` / `PublishQuestion()` | `Platform` 接口 |

### 名词 → 实体/参数

| 用户原话名词 | 代码角色 | 落地的实体 |
|---|---|---|
| 招聘需求 | 领域实体 | `JobPost` |
| 面试题 | 领域实体 | `InterviewQuestion` |
| 知识点 | 领域实体 | `Knowledge` |
| 数据源 | 领域实体 | `Source` |
| 平台 | 策略接口 | `Platform` |
| 任务 | 领域实体 | `Task` |

## 三、变化因子识别

变化因子是架构设计的核心输入——"哪里会变，就在哪里画线"。

| 变化点 | 变化频率 | 用户原话信号 | 应对策略（隔离方式） |
|---|---|---|---|
| **数据源类型** | 高 | "后续还会拓展" | `Spider` 接口 + `SpiderRegistry` 注册表 |
| **AI 加工逻辑** | 高 | "整理出面试题"、"总结为知识点" | `AIGenerator` 接口，Prompt 在适配器层 |
| **推送平台** | 高 | "便于后续添加其他平台" | `Platform` 接口 + `PlatformRegistry` |
| **爬虫框架** | 中 | 隐含（colly 可换 chromedp） | `Spider` 接口隔离 |
| **存储方案** | 中 | 隐含（MySQL 可换） | `*Repository` 接口隔离 |
| **LLM 厂商** | 中 | "trpc-agent-go 框架" | `openai.WithBaseURL` 支持任意兼容端点 |
| **业务规则** | 低 | "招聘需求要有职位和要求" | 实体层 `IsValid()` 领域规则 |

**关键结论**：业务规则最稳定，数据源/AI/推送平台最易变。这直接决定了整洁架构的边界划分——易变的外部依赖全部用接口隔离。

## 四、目标用户群体分析

采用"同心圆"模型，从核心人群向外扩展：

```
                    ┌─────────────────────────────────┐
                    │  第三圈层：内容消费者              │
                    │  （读到推送文章/面试题的学习者）    │
                    │  ┌───────────────────────────┐  │
                    │  │  第二圈层：内容创作者        │  │
                    │  │  （技术博主、培训师）         │  │
                    │  │  ┌───────────────────────┐ │  │
                    │  │  │  核心人群：项目维护者    │ │  │
                    │  │  │  （采集+加工+推送运营） │ │  │
                    │  │  └───────────────────────┘ │  │
                    │  └───────────────────────────┘  │
                    └─────────────────────────────────┘
```

| 圈层 | 用户画像 | 核心诉求 | WebReaper 提供的能力 |
|---|---|---|---|
| **核心人群** | 项目维护者/运营 | 一键采集→加工→推送，多平台分发 | 4 个用例的完整闭环 + REST API |
| **第二圈层** | 技术博主/培训师 | 把自己的内容快速分发到多平台 | 多平台推送 + 内容格式转换 |
| **第三圈层** | 学习者 | 读到高质量的面试题/知识点 | 推送平台上的结构化内容 |

## 六、与 AgentCore 的关系

WebReaper 与姊妹项目 AgentCore 形成**上下游关系**：

```
WebReaper（数据采集与加工）          AgentCore（Agent 核心平台）
┌──────────────────────┐            ┌──────────────────────┐
│ 采集 → AI加工 → 推送  │ ──推送──→  │ 内容接入网关          │
│ (招聘需求/知识点)     │            │ (面试题/知识点/面经)   │
└──────────────────────┘            └──────────────────────┘
```

WebReaper 的"多平台推送"功能，其中一个推送目标正是 AgentCore 的内容接入网关（`POST /api/v1/ingest/*`）。两个项目共享相同的整洁架构理念和技术栈（Go + trpc-agent-go）。
