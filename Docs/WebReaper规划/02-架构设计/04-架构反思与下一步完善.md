# 架构反思与下一步完善

> 📌 架构是持续演进的。本文档记录当前架构的问题清单（按严重度分级）和改进方向。
> 与 [01-整洁架构符合性分析](01-整洁架构符合性分析.md) 互补：那篇做体检，这篇列整改。

## 一、当前架构健康度

**骨架优秀，血肉待补。** 整洁架构的"宪法"（依赖向内）执行得很好，但有几个功能空壳和生产基础设施缺口需要填补。

## 二、问题清单与改进方向

### 🔴 P0 严重（影响核心功能可用性）

| # | 问题 | 现状 | 风险 | 改进方向 | 落点 |
|---|---|---|---|---|---|
| 1 | **异步任务子系统空壳** | TaskQueue/TaskRepository 已实现但无消费方，4 用例全同步执行 | 采集/AI 耗时操作阻塞 HTTP 请求，长任务超时 | 实现任务消费 worker，用例支持异步投递 | `cmd/server/worker.go` + 用例增加 `ExecuteAsync` |
| 2 | **无统一日志抽象** | 用 `fmt.Printf`/`log.Fatalf`，go.mod 已引 zap(间接) 但未用 | 无法结构化日志、无法调级别、无法接 ELK | 引入 `port.Logger` 接口 + zap 适配器 | `usecase/port/logger.go` + `adapter/logger/` |

### 🟡 P1 中等（上线前应解决）

| # | 问题 | 现状 | 风险 | 改进方向 | 落点 |
|---|---|---|---|---|---|
| 3 | **无认证鉴权** | JWTConfig 预留但无 auth 中间件，API 裸奔 | 任何人可调采集/推送接口 | 实现 JWT 中间件 + 用户实体 | `adapter/handler/middleware/` |
| 4 | **AutoMigrate 生产风险** | 启动时自动建表/改表 | 生产环境表结构变更不可控 | 改用 goose/atlas 迁移工具 + 版本化 SQL | `migrations/` 目录 |
| 5 | **无监控/链路追踪** | OpenTelemetry 全套在 go.mod(间接) 但零引用 | 故障无法定位，LLM 调用烧钱无法监控 | 接入 OTel trace + 自定义 metric（Token 消耗）| `adapter/telemetry/` |
| 6 | **HTTPPlatform 真实实现未接线** | 代码完整可用但 main 只注册 MockPlatform | 推送功能实际不工作 | 填真实 URL/Key 后在 main 注册 | `cmd/server/main.go` |

## 四、架构演进原则（不变的铁律）

无论怎么演进，以下 4 条铁律不能违背：

1. **依赖永远向内**：任何新功能，外部依赖必须通过 port 接口隔离，domain/usecase 零框架 import
2. **双实现降级保留**：新增真实适配器时，mock 实现保留，保证零配置可启动
3. **扩展用加法不用改法**：新增类型走"实现接口 + 注册"，不改已有用例
4. **测试先行**：每个新适配器/用例都要有对应测试，用例测试用 mock 注入

## 五、一句话总结

> 架构骨架已经为所有后续功能预留了正确的扩展点——剩下的是"填血肉"（异步任务、日志、认证、前端），而不是"动骨架"。这正是整洁架构的价值：**前期投入的分层成本，在后续迭代中以"零修改"的方式持续回报**。
