# 整洁架构符合性分析

> 📌 基于 Robert C. Martin《整洁架构之道》第 15 章，对 WebReaper 当前架构做系统体检。
> 评分标准：依赖方向是否向内、业务核心是否可独立测试、是否可推迟/替换技术决策。

## 一、总体评分：A-

| 维度 | 评分 | 说明 |
|---|---|---|
| 依赖方向铁律 | ⭐⭐⭐⭐⭐ | grep 验证零违规，domain/usecase 完全不知道框架存在 |
| 依赖倒置 DIP | ⭐⭐⭐⭐⭐ | 7 个 port 接口全部由用例声明、适配器实现 |
| 可独立测试 | ⭐⭐⭐⭐⭐ | 56 个测试，用例层全用 mock 注入，脱离 DB/HTTP 可测 |
| 可推迟/替换决策 | ⭐⭐⭐⭐⭐ | 双实现降级是亮点（真实/mock 一键切换）|
| 业务核心纯净度 | ⭐⭐⭐⭐ | domain 零框架标签，但 `PublishRecord` 放在 port 包是轻微异味 |
| 生产基础设施 | ⭐⭐ | 无日志抽象/监控/认证，AutoMigrate 不适合生产 |
| 功能完整度 | ⭐⭐⭐ | 4 用例闭环，但异步任务空壳、前端未做 |

**综合 A-**：架构骨架极其扎实，短板集中在迭代进度（异步任务/前端/生产基础设施）而非架构设计本身。

## 三、依赖铁律检验（源码证据）

### 检验 1：domain 层零框架依赖

```bash
# 验证命令
grep -rE "colly|gorm|gin|chromedp|trpc|milvus|net/http" internal/domain/
# 结果：零命中 ✅
```

domain 层只 import 标准库（`time`/`strings`/`crypto`）和同层 valueobject，完全不知道 colly/gorm/gin/trpc 的存在。

### 检验 2：usecase 层零框架依赖

```bash
grep -rE "colly|gorm|gin|chromedp|trpc|milvus|net/http" internal/usecase/
# 结果：零命中 ✅
```

usecase 层只 import `domain` 和 `port`（自己声明的接口），不知道任何具体实现。

### 检验 3：领域实体零 GORM 标签

```bash
grep -rn "gorm:" internal/domain/
# 结果：零命中 ✅
```

实体保持纯净，GORM 标签全部在 `adapter/repository/model.go` 的 PO（持久化对象）上，通过 mapper 双向转换。

## 四、依赖倒置 DIP 检验

整洁架构的核心：**接口归用例所有，实现在适配器层**。

| port 接口 | 声明位置（用例层） | 实现位置（适配器层） | 隔离的框架 |
|---|---|---|---|
| `Spider` | `usecase/port/spider.go` | `adapter/spider` (colly) + `mock` | colly/chromedp |
| `AIGenerator` | `usecase/port/ai_generator.go` | `adapter/ai` (trpc-agent-go) + `mock` | trpc-agent-go |
| `Platform` | `usecase/port/platform.go` | `adapter/publish` (HTTP) + `mock` | 外部推送 API |
| `*Repository` (5个) | `usecase/port/repository.go` | `adapter/repository` (GORM) + `mock` | MySQL/SQLite |
| `TaskQueue` | `usecase/port/task_queue.go` | `mock` (channel) | Redis/Kafka |
| `SpiderRegistry` | `usecase/port/registry.go` | — | 数据源扩展点 |
| `PlatformRegistry` | `usecase/port/platform.go` | — | 平台扩展点 |

**结论**：所有外部依赖都通过 port 接口隔离，更换任何框架时用例层零修改。

## 五、架构体检四问

参考第 15 章的标准检验（"四个能不能"）：

| # | 检验问题 | WebReaper 的回答 | 通过？ |
|---|---|---|---|
| 1 | 换数据库，业务核心要不要改？ | 否。换 MySQL→PostgreSQL 只改 `adapter/repository` 的 PO 和驱动 | ✅ |
| 2 | 换 Web 框架，业务逻辑要不要改？ | 否。换 Gin→Echo 只改 `adapter/handler` | ✅ |
| 3 | 能否脱离 Web/DB 做纯单元测试？ | 能。56 个测试全用 mock 注入，`go test` 不需要 MySQL/Gin | ✅ |
| 4 | 接入新外部系统，要不要改业务代码？ | 否。新增爬虫/平台只需实现接口+注册，用例零改 | ✅ |

**四问全过**：这是整洁架构兑现的核心承诺。

## 六、设计模式应用评价

| 模式 | 应用位置 | 应用质量 |
|---|---|---|
| **策略模式** | Spider/Platform/AIGenerator 接口 | ⭐⭐⭐⭐⭐ 完美隔离外部依赖 |
| **注册表模式** | SpiderRegistry/PlatformRegistry | ⭐⭐⭐⭐⭐ 开闭原则落地，扩展零改用例 |
| **适配器模式** | 全部 adapter/* | ⭐⭐⭐⭐⭐ PO↔Entity 的 mapper 是教科书级 |
| **谦卑对象** | handler/*Controller | ⭐⭐⭐⭐⭐ 纯数据搬运，零业务逻辑 |
| **状态机** | TaskStatus 值对象 | ⭐⭐⭐⭐ 定义完整，但用例未消费（空壳）|
| **函数选项** | NewHTTPPlatform/NewTrpcAgentGenerator | ⭐⭐⭐⭐ 标准 Go 惯用法 |

## 七、存在的问题与瑕疵

| 问题 | 严重度 | 详见 |
|---|---|---|
| `PublishRecord` 实体放在 port 包 | 🟢 低 | 应移至 domain 或独立聚合 |
| main.go 端口硬编码 `:8082` 未读 config | 🟡 中 | config.Server.Port 已加载但未使用 |
| `statusForError` 用字符串匹配 binding 错误 | 🟡 中 | 应改用 `errors.As` 类型断言 |
| Spider OnError 回调空实现 | 🟡 中 | 采集错误被静默吞掉 |
| AI 适配器直接依赖 config 包 | 🟢 低 | 可抽 Logger/KeyProvider 接口降低耦合 |
| AutoMigrate 生产风险 | 🟡 中 | 应改用 goose/atlas 迁移工具 |

## 八、结论

WebReaper 的整洁架构执行度在同类项目中属于**优秀水平**：

1. **依赖方向零违规**（最难做到的，已经做到）
2. **双实现降级策略**是真正的工程亮点——让系统既能连真实 MySQL/MiniMax，也能零配置启动
3. **可测试性极佳**——56 个测试覆盖了从领域规则到 HTTP 端到端的各层
4. **扩展性设计到位**——新增爬虫/平台/AI 厂商都是"加法"而非"改法"

主要提升空间在**迭代进度**（异步任务、前端、生产基础设施）而非架构本身。架构骨架已经为这些后续功能预留了正确的扩展点。
