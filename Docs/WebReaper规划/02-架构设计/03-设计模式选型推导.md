# 设计模式选型推导

> 📌 用五步分析法（拆解核心要求→寻找变化因子→提取多态信号→识别隔离壁→推导匹配）逐模块推导设计模式。
> 方法论来源：架构师手册 `02-requirement-analysis.md`。

## 一、推导总览

| 模块 | 核心要求 | 变化因子 | 多态信号 | → 模式 |
|---|---|---|---|---|
| ① 采集 | 流程固定：爬取→校验→去重→入库 | 数据源会新增 | 按 SourceType 选爬虫 | **策略+注册表** |
| ② AI 加工 | 流程固定：取数据→调AI→校验→入库 | Prompt/模型会变 | 按 LLM 厂商切换 | **策略** |
| ③ 推送 | 流程固定：查内容→去重→分发→记录 | 平台会新增 | 按 PlatformName 选平台 | **策略+注册表** |
| ④ 持久化 | CRUD + 去重查询 | 存储可换 | — | **仓储接口**（依赖倒置）|
| ⑤ 任务调度 | 异步执行耗时操作 | 队列可换 | — | **队列接口**（依赖倒置）|
| ⑥ Web 接入 | HTTP↔用例 数据搬运 | 框架可换 | — | **谦卑对象** |

## 二、模块 ① 采集：策略+注册表

### ① 拆解核心要求
- 动词：爬取 → `Crawl()`
- 名词：数据源、招聘需求 → 参数
- 流程骨架：爬取 → 逐条校验 → 指纹去重 → 批量入库

### ② 寻找变化因子
- "后续还会拓展" → 数据源类型会横向新增（Boss/拉勾/掘金/通用网页）

### ③ 提取多态信号
- "按 SourceType 选择爬虫" → 运行时按类型分派

### ④ 识别隔离壁
- 不想在用例里写 `if sourceType == "boss" { ... } else if ...`
- 爬虫库（colly/chromedp）是最易变、最难测的部分，必须隔离

### ⑤ 推导匹配
- 因为"流程骨架固定" → 定义 `Spider` 接口
- 因为"算法会横向新增" → 必须多态
- 因为"按类型分派" → 引入 `SpiderRegistry` 注册表

**推导结论**：**策略模式（Spider 接口）+ 注册表（SpiderRegistry）**

```go
// usecase/port/spider.go —— 接口归用例所有
type Spider interface {
    Crawl(ctx context.Context, source entity.Source) ([]entity.JobPost, error)
    Supports() string
}

// usecase/port/registry.go —— 注册表
type SpiderRegistry struct { ... }
func (r *SpiderRegistry) Register(s Spider) { ... }
func (r *SpiderRegistry) Lookup(sourceType string) (Spider, bool) { ... }
```

## 三、模块 ② AI 加工：策略

### ② 寻找变化因子
- Prompt 会迭代（生成面试题的提示词）
- LLM 模型会换（MiniMax/OpenAI/智谱）
- 框架可能升级（trpc-agent-go 版本）

### ③ 提取多态信号
- "用 trpc-agent-go 框架" → 但框架细节要隔离

### ④ 识别隔离壁
- Prompt 工程不想污染用例
- LLM 调用是最难测的部分（需要 API Key、烧钱）

### ⑤ 推导匹配
- 定义 `AIGenerator` 接口，用例只依赖它
- Prompt 构造 + JSON 解析全部放在 `adapter/ai/` 适配器层

**推导结论**：**策略模式（AIGenerator 接口）+ Prompt 工程隔离**

```go
type AIGenerator interface {
    GenerateQuestions(ctx context.Context, post entity.JobPost) ([]entity.InterviewQuestion, error)
    SummarizeKnowledge(ctx context.Context, rawText string, sourceURL string) (entity.Knowledge, error)
}
```

## 四、模块 ③ 推送：策略+注册表

### ② 寻找变化因子
- "便于后续添加其他平台" → 平台会横向新增

### ③ 提取多态信号
- "按平台名选择推送方式" → 运行时按名称分派

### ④ 识别隔离壁
- 每个平台的认证/请求体结构/错误处理都不同
- 外部 HTTP 调用必须隔离

### ⑤ 推导匹配
- 与模块①完全同构：**策略（Platform）+ 注册表（PlatformRegistry）**

**推导结论**：**策略模式 + 注册表**（与 Spider 完全同构的设计）

```go
type Platform interface {
    Name() string
    PublishArticle(ctx context.Context, article entity.Knowledge) (valueobject.PublishResult, error)
    PublishQuestion(ctx context.Context, question entity.InterviewQuestion) (valueobject.PublishResult, error)
}
```

## 五、模块 ④ 持久化：仓储接口（依赖倒置）

### 推导
存储是会变的（MySQL→PostgreSQL→加 ES/向量库），但 CRUD 契约稳定。
因此定义 `*Repository` 接口，用例依赖接口，GORM 在适配器实现。

**关键设计**：PO（持久化对象）与领域实体分离。领域实体零 GORM 标签，PO 带 GORM 标签，mapper 双向转换。

## 六、模式选型总表

| 模式 | 应用位置 | 解决的问题 | 为什么不用别的 |
|---|---|---|---|
| 策略 | Spider/AIGenerator/Platform | 隔离"会横向新增"的外部依赖 | 不用 if-else（违反开闭）|
| 注册表 | SpiderRegistry/PlatformRegistry | 运行时按 key 分派 | 不用工厂（key 简单，无需复杂创建）|
| 适配器 | 全部 adapter/* | 接口不兼容转换 | — |
| 谦卑对象 | handler/*Controller | 让 HTTP 可测（剥到只剩搬运）| — |
| 函数选项 | NewHTTPPlatform 等 | 可选参数配置 | 不用 Builder（参数不多）|

## 七、验证清单（防过度设计）

| 检查项 | 结果 |
|---|---|
| 每个模式收益 > 复杂度？ | ✅ 策略+注册表让新增类型是"加法" |
| 没有为了模式而模式？ | ✅ TaskQueue 接口虽预留但实现只有 mock，未过度抽象 |
| 团队能理解？ | ✅ 策略+注册表是 Go 最常见模式 |
