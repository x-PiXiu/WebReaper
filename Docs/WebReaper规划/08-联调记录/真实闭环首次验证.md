- ✅ `prompt_tokens` / `completion_tokens` / `total_tokens` 全部正确累加。

## 三、踩到的坑（真实记录）

### 坑 1：LLM 输出含 `<think>` 推理标签
MiniMax 的回复前面带 `<think>...</think>` 推理过程，再跟正式 JSON。当前 `process.ProcessItem` 的 `extractJSON` 只取 `{...}`，能正确提取，但**推理内容消耗了 token**（459 prompt 里可能含历史，464 completion 里含推理）。

**待改进**：若要省 token，可换用不支持推理的模型，或在 prompt 里明确"不要推理过程"。

### 坑 2：终端中文乱码（非架构问题）
Windows GBK 终端下中文显示为乱码，是 Go 默认 UTF-8 输出与终端编码不符。**不影响功能**，部署到 Linux 或改终端编码即正常。

### 坑 3：arbeitnow 数据含 HTML 转义
description 字段是 HTML（`<p>...</p>`），不是纯文本。当前直接喂给 LLM 没问题（LLM 能理解），但若要更精准，可加一层 HTML→纯文本清洗。

## 四、架构验证发现

### 确认可用的部分
1. **api_crawler 真实采集**：直接调 REST API 拿 JSON，无需 auth、合规、稳定。
2. **publish 双模式**：raw 模式（原样转发 JSON）验证通过，mapping 模式未测但同路径。
3. **降级机制**：未配 LLM 时脚本优雅跳过 AI 步骤（联调脚本设计如此）。
4. **Token 监控**：流 B 的实现正确，日志+trace 双通道。

### 暴露的待改进项（喂给后续优先级）
1. **推送层无重试**（流 C）：本次接收端一次成功，但真实外部系统偶发 5xx 会直接失败。**优先级提升**——验证了这是真实需求。
2. **无 HTML 清洗**：采集到的 description 含 HTML 标签，喂 LLM 浪费 token。可加一个清洗步骤。
3. **LLM 推理 token 浪费**：MiniMax 的 `<think>` 推理消耗约一半 completion token，是否可关需评估。
4. **代理池**（流 D）：本轮用 arbeitnow（无反爬）没触发需求。若后续碰弱反爬站才需要。
