## 二、架构决策记录（ADR）

### ADR-001：采用整洁架构四层分层

- **状态**：✅ 已采纳
- **背景**：系统需支持多种数据源、多平台、多 LLM，外部依赖易变
- **决策**：domain/usecase/port/adapter 四层，依赖向内，外部依赖全用接口隔离
- **权衡**：分层增加代码量，但换来可测试性和可替换性

### ADR-002：双实现降级策略

- **状态**：✅ 已采纳
- **背景**：开发环境不一定有 MySQL/LLM API Key
- **决策**：每个适配器提供"真实 + mock"双实现，配置缺失自动降级 mock
- **权衡**：多维护一套 mock，但保证零配置可启动、CI 无外部依赖

### ADR-003：PO 与领域实体分离

- **状态**：✅ 已采纳
- **背景**：GORM 标签会污染领域实体，违反整洁架构
- **决策**：定义独立的 PO（持久化对象），通过 mapper 与领域实体双向转换
- **权衡**：多一层转换代码，但领域实体保持纯净

### ADR-004：trpc-agent-go 放在最外层适配器

- **状态**：✅ 已采纳
- **背景**：LLM 框架是重依赖，且会升级
- **决策**：用例只依赖 `port.AIGenerator` 接口，trpc-agent-go 调用在 `adapter/ai/`
- **权衡**：无法直接用框架高级特性（如多 Agent 协作），但隔离了框架风险

### ADR-005：MiniMax 通过 OpenAI 兼容协议接入

- **状态**：✅ 已采纳
- **背景**：trpc-agent-go 默认支持 OpenAI，MiniMax 兼容 OpenAI 协议
- **决策**：通过 `openai.WithBaseURL("https://api.minimaxi.com/v1")` 接入
- **权衡**：无法用 MiniMax 私有特性，但换厂商只需改配置

## 三、不做什么（明确拒绝）

| 拒绝项 | 理由 |
|---|---|
| ❌ 不做分布式微服务 | 当前规模用单体足够，微服务增加运维成本 |
| ❌ 不做 ORM 之外的查询构造器 | GORM 够用，不引入 sqlx/jet 等增加学习成本 |
| ❌ 不做自研爬虫框架 | colly 成熟，自研是重复造轮子 |
| ❌ 不做图形化爬虫配置界面 | CSS 选择器配置化已足够灵活 |
| ❌ 不做实时推送（WebSocket） | 当前是批量推送场景，HTTP 足够 |
| ❌ 过早接入向量库 | 知识点数据量未起来，向量检索是过度设计 |
