# 27 - 架构与业务优化归总

> 基于整洁架构（Clean Architecture）对 WebReaper 服务端的系统性审查，归总架构改进与业务完善两个维度的优化事项。
> 审查范围：444 个 Go 源文件，覆盖生成/发布/GEO/计费/智能体五大核心域。

---

## 一、架构优化（代码质量 × 可维护性）

| 优先级 | 问题 | 当前状态 | 建议 | 影响范围 |
|--------|------|---------|------|---------|
| **A-P0** | `main.go` 装配逻辑过重 | 1350 行，条件嵌套 5 层深 | 拆 `bootstrap/` 包：`initGeneration()` / `initGEO()` / `initPublish()` / `initBilling()` / `initScheduler()`，main 只留骨架 | 全局 |
| **A-P0** | usecase Setter 注入过多 | `geoContentUC` 有 12 个 SetXxx | 改 Functional Options：`NewContentUC(gen, scorer, repo, WithCache(c), WithRAG(r))` | usecase 层 |
| **A-P1** | 实体层贫血 | 状态转换散落在 usecase | entity 增 `GenerationTask.TransitionTo(newState)` / `Account.Revive()` 等 | domain 层 |
| **A-P1** | `GenerationParams map[string]any` | 17 个端点参数全靠 map 透传 | 高频端点（text2video/digital_human/tts）定义强类型 struct | domain + usecase |
| **A-P2** | port 包 40+ 文件平铺 | 查找接口需遍历目录 | 按域聚合：`port_gen.go` / `port_account.go` / `port_geo.go` / `port_publish.go` | port 层 |
| **A-P2** | Repository 映射手动维护 | 每个实体 ToPO/FromPO 手写 | 考虑 ent/sqlc 代码生成，或 struct tag 反射映射 | adapter/repository |
| **A-P3** | 部分 Handler 依赖具体 usecase | `*generation.GenerationUseCase` 裸引用 | 改为依赖 port 接口，提升可测试性 | adapter/handler |

## 二、业务优化（功能完善 × 商业闭环）

### 生成域

| 优先级 | 完善项 | 缺口描述 | 实现复杂度 |
|--------|--------|---------|-----------|
| **B-P0** | 资产物化（Plan-26） | `creations_json` 内嵌产物，无法独立查询/管理分身和音色 | 中 |
| **B-P0** | 个人分身列表 | `ListOfficialSubjects()` 只查官方，个人分身需从 tasks 聚合——缺 `ListPersonalSubjects()` | 低 |
| **B-P0** | 硬编码治理 | 默认音色 `female-shaonv`、分辨率 `1080p`、比例 `16:9`、端点中文名等散落 6 处 | 低 |
| **B-P1** | 模型差异化计费 | q3-pro 和 q1 统一按"次"计费，成本不分级 | 中 |

### 发布域

| 优先级 | 完善项 | 缺口描述 | 实现复杂度 |
|--------|--------|---------|-----------|
| **B-P1** | 抖音 API 发布通道 | OAuth 已就绪，缺 `PublishChannel` 实现——当前只能 RPA | 中 |
| **B-P1** | 平台内容配置 DB 化 | `DefaultPlatformConfigs` 硬编码 3 个平台，运营不可调 | 低 |
| **B-P2** | 生成→发布→监测自动闭环 | 生成完成后需手动发布，缺自动排期→发布→监测→反馈链路 | 高 |

### GEO 域

| 优先级 | 完善项 | 缺口描述 | 实现复杂度 |
|--------|--------|---------|-----------|
| **B-P2** | 内容优化 A/B 测试 | 同品牌多版本内容无法对比 AI 引擎提及率差异 | 高 |
| **B-P2** | 评价数据接入 | 大众点评/美团评价是本地信任信号，未接入 | 高 |
| **B-P3** | 多模态监测 | 只测文本回答，AI 搜索已支持图片/视频回答 | 高 |

### 智能体域

| 优先级 | 完善项 | 缺口描述 | 实现复杂度 |

| **B-P3** | 评论监控与自动回复 | 发布后用户评论是获客触点，无监控能力 | 高 |

## 四、依赖关系图

```
① 个人分身列表 ──→ ⑦ 资产物化（先聚合查询，后建独立表）
② 硬编码治理   ──→ ⑨ 抖音 API 通道（平台配置 DB 化后发布通道更灵活）
③ main 拆包    ──→ ⑧ Options 重构（拆包后各域独立 Options 改造）
④ Agent 任务工具 ──→ ⑤ Agent B-Roll 工具（共享任务查询基础设施）
⑦ 资产物化     ──→ ⑬ 自动闭环（独立资产表是自动发布的前提）
⑩ 差异化计费   ──→ ⑭ A/B 测试（计费粒度细才能按版本计成本）
```

**推荐执行顺序**：①②③ 并行 → ④⑤⑥ 并行 → ⑦⑧ → ⑨⑩ → ⑪⑫ → ⑬⑭ → ⑮-⑳

## 五、整洁架构合规度基线

### 5.1 依赖规则（Dependency Rule）

```
handler → usecase → domain/entity     ✅
handler → usecase/port                ✅
adapter/repository → domain/entity    ✅
adapter/provider → usecase/port       ✅
domain/entity → (无外部依赖)           ✅
```

### 5.2 依赖倒置（DIP）执行度

| 领域 | 接口定义方 | 实现方 | 倒置质量 |
|------|-----------|--------|---------|
| 生成任务仓储 | `usecase/port` | `adapter/repository` | ⭐⭐⭐ |
| 生成服务商 | `usecase/port` | `adapter/provider` | ⭐⭐⭐ |
| 端点策略 | `usecase/port` | `adapter/viduendpoint` | ⭐⭐⭐ |
| 发布通道 | `usecase/port` | `adapter/publisher` | ⭐⭐⭐ |
| AI 生成器 | `usecase/port` | `adapter/ai` | ⭐⭐⭐ |
| 媒体存储 | `usecase/port` | `adapter/storage` | ⭐⭐⭐ |
| 缓存 | `usecase/port` | `adapter/cache` | ⭐⭐⭐ |
| 分布式锁 | `usecase/port` | `adapter/lock` | ⭐⭐⭐ |
| 支付网关 | `usecase/port` | `adapter/payment` | ⭐⭐⭐ |

### 5.3 开闭原则（OCP）实践

- 新增生成端点 = 新增 `EndpointAdapter` 实现 + 注册一行
- 新增发布平台 = 实现 `PublishChannel` 接口 + `channelRegistry.Register()` 一行
- 新增定时任务 = 实现 `port.ScheduledTask` + `taskScheduler.Register()` 一行
- 新增爬虫工具 = 实现 `port.CrawlerTool` + `toolRegistry.Register()` 一行

### 5.4 降级链完备性

| 场景 | 降级路径 |
|------|---------|
| Redis 连接失败 | → NoopLock / 内存 nonce / 无缓存 |
| DB 未配置 | → mock 仓储 |
| LLM 未配置 | → mock AI |
| Vidu 未配 Key | → MockProvider（前端全流程可演示） |
| ffmpeg 不可用 | → 降级路径（≤25MB 视频直传 ASR） |
| 高德未配 Key | → mock 降级（门店 pending，附近同行仅 AI 榜） |
