# 12 - 灵感广场与热门同款重构方案

> 日期：2026-08-24 | 状态：**已实现（核心功能）** | 优先级：P1
> 实际实现日期：2026-08-24 | 实现代码：见 Docs/Plans/13-可规模化爬虫架构设计方案.md

## 一、问题分析

### 1.1 当前实现的问题

从服务器日志和代码分析，当前热门同款功能存在以下问题：

| # | 问题 | 日志证据 | 影响 |
|---|------|----------|------|
| 1 | 抖音站内搜索全部返回 0 结果 | `search "正宗川味" -> 0 items (status=0)` | 功能完全不可用 |
| 2 | LLM curate 思考标签泄露 | `curate LLM 响应首部=<think>` | curate 判空，降级为文章参考 |
| 3 | LLM 筛选失败导致空结果 | `curate 完成：videos=0` | 用户看到空列表 |
| 4 | 无品牌隔离 | 所有品牌共用搜索逻辑 | 不同品牌看到相同内容 |
| 5 | 无数据持久化保障 | 依赖内存缓存，重启丢失 | 用户体验差 |
| 6 | 无实时数据刷新 | 播放量/点赞只采集一次 | 数据过时 |

### 1.2 核心架构问题

```
当前（有问题）：
用户请求 → 现场搜索 → LLM筛选 → 内存缓存 → 返回
           ↓ 失败
         空结果

目标（重构后）：
用户请求 → DB查询 → 返回（快速响应）
定时任务 → 关键词生成 → 搜索采集 → 全量入库 → 定期刷新
首次触发 → DB为空时自动触发采集
```

### 4.2 核心流程

#### 首次触发流程

```
用户 GET /api/v1/inspirations?brand_id=xxx
  → InspirationUseCase.List(ctx, brandID)
    → repo.ListByBrand(ctx, brandID, opts)
      → 结果为空？
        → 是：触发异步采集 goroutine
             → generateKeywords(brand)  // LLM 生成关键词
             → crawler.Search(keywords) // 抖音搜索
             → repo.SaveBatch(videos)   // 全量入库
             → repo.LinkBrand(videos, brandID) // 建立关联
        → 返回空列表（前端显示"采集中..."）
        → 否：返回数据
```

#### 定时采集流程

```
定时任务（每 6 小时）
  → 遍历所有品牌的采集配置
    → 判断是否到达采集间隔
      → 是：generateKeywords(brand) + crawler.Search(keywords)
            → 去重后追加新数据
      → 否：跳过
  → 遍历需要刷新的旧数据（12 小时未刷新）
    → crawler.RefreshMetrics(videoURLs)
    → repo.UpdateMetrics(videos)
```

#### 爆款指数计算

```go
// viral_score 综合互动率计算（0-100）
func calculateViralScore(play, digg, comment, share, collect int64) float64 {
    if play == 0 {
        return 0
    }
    // 互动率权重：点赞 40% + 评论 25% + 分享 20% + 收藏 15%
    engageRate := float64(digg)*0.4 + float64(comment)*0.25 + float64(share)*0.2 + float64(collect)*0.15
    rate := engageRate / float64(play) * 100
    // 归一化到 0-100（假设 5% 互动率 = 100 分）
    score := rate / 5.0 * 100
    if score > 100 {
        score = 100
    }
    return math.Round(score*10) / 10
}
```

### 4.3 定时任务设计

| 任务 | 频率 | 逻辑 |
|------|------|------|
| `inspiration-crawl` | 每 6 小时 | 遍历品牌 → 判断间隔 → 搜索采集 → 去重入库 |

### 4.5 去抖音 LLM curate 的理由

当前流程：
```
搜索 → LLM筛选 → 返回（LLM失败=空结果）
```

重构后流程：
```
搜索 → 全量入库 → 按 viral_score 排序 → 返回
```

**去掉 LLM 筛选的原因**：
1. LLM 响应不稳定（think 标签泄露、响应格式不一致）
2. LLM 调用有成本（每次 2000+ tokens）
3. 数据本身已有播放量/点赞等客观指标，排序比 LLM 主观筛选更可靠
4. LLM 仅用于关键词扩展（输入端），不用于筛选（输出端）

## 六、实际实现 vs 设计方案差异

| 设计方案 | 实际实现 | 差异说明 |
|----------|----------|----------|
| 单平台爬虫（抖音） | 三平台爬虫（抖音/快手/B站） | 超出预期，参考 MediaCrawler 实现 |
| `port.InspirationCrawler` | `port.CrawlerPlatform` | 更通用的接口设计 |
| 简单定时任务 | StaggeredScheduler + Worker Pool | 更强的调度能力 |
| 无账号管理 | `crawler_accounts` + 扫码登录 | 平台方账号统一管理 |
| 无签名算法 | WBI/__NS_hxfalcon/a_bogus | 三平台签名完整实现 |
| 6 小时间隔 | 15 分钟间隔 + 夜间加速 | 更频繁的数据更新 |
| 无详情 API | `HandleRefreshMetrics` | 补充搜索 API 缺失字段 |
| LLM 筛选结果 | 去掉 LLM，按数据排序 | 更可靠，无 LLM 依赖 |

## 八、风险与依赖

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 抖音反爬升级 | 搜索无结果 | 多账号轮换、频率限制、降级到通用搜索 |
| 视频数据获取不全 | 缺少播放量等字段 | 优先获取基础数据，互动数据异步补充 |
| LLM 关键词生成质量差 | 搜索结果不相关 | 人工可配置额外关键词、关键词黑名单 |
| 数据量增长过快 | 存储压力 | 30 天自动清理、按品牌分页 |
