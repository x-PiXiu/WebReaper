## 二、行业调研（v2 扩充）

### 2.1 摘星 GEO（合肥摘星AI，龙吟集团旗下）

调研来源：2026 年行业评测与官方新闻资料。

**产品体系**：摘星方舟·企业AI营销SaaS平台（核心模块"摘星搜荐·GEO+SEO全域搜索营销"），技术底座为自研"摘星万象·企业AI营销垂直大模型"（基于讯飞星火）。

**设计思想与功能要点**：

1. **三位一体智能营销网络**：大模型 GEO（New Bing/Perplexity 等 AI 搜索入口）+ 短视频 SEO（抖音/视频号）+ 传统 SEO（百度/谷歌）
2. **五部曲方法论**：立身份 → 建资产 → 布信源 → 发全域 → 盯数据（闭环、可追踪、可归因），每步对应 SaaS 模块
3. **「语义份额驾驶舱」（V3.0 核心新增）**：实时查看品牌在各类 AI 搜索引擎中的**提及率、情感倾向、竞品对比数据**——官方称这解决了"AIGEO 效果难以量化"的行业痛点，"让 AI 搜索获客从凭感觉走向靠数据"
4. **全链路数据看板**：从流量入口到成交转化的 ROI 看板
5. **统一内容管理后台**："一次生产、多平台适配"（V3.0 新增对多家主流 AI 搜索引擎的深度适配）
6. **AI 知识库定向植入**：企业产品/案例/资质结构化植入豆包、DeepSeek、文心一言等 11 个智能平台知识库
7. **目标客群画像**：线下连锁品牌、本地服务商、制造业与消费品牌、预算有限的中小企业——**与 WebReaper 目标客群高度重合**

**对规划的关键启示**：
- "语义份额驾驶舱"证明了**情感倾向（情绪维度）与竞品对比**是驾驶舱的标配，WebReaper 当前缺情感维度
- 五部曲与 WebReaper 功能一一对应，界面应显性化闭环流程

### 2.2 新榜智汇 Geowise（geo.newrank.cn）——最具体的产品设计参照

新榜旗下企业级 GEO 优化与效果评估 SaaS（2026 年 1 月推出，虎啸奖得主，参编《生成引擎优化（GEO）团体标准》），面向 500 强与中大型企业、营销代理商。

**六大核心模块（界面与功能）**：

| 模块 | 功能 | 界面形态 | 对标 WebReaper |
|---|---|---|---|
| Geo 速查工具 | 批量提交品牌问题→一键获取豆包/元宝/DeepSeek/Kimi/千问/百度AI 六平台回复，含能见度/提及位次/情绪倾向/引用信源 | 问题提交列表 + 六平台并排结果卡 | 监测有采样矩阵，但**无"单次速查"轻量入口**、无位次/情绪维度 |

- 数据纯净：10000+ 无污染代理节点、自动化查询集群、排除个人化记忆干扰，**数据可复现、可核验**
- 跨平台统一口径：六大引擎同源比对，统一抓取规则与统计逻辑
- 信源全链路溯源：AI 回答引用链接一键溯源，区分**官网/权威垂类媒体/第三方自媒体**来源
- 语义级分析：自动拆解 AI 回答顺位、情感倾向、竞品对比语境、用户真实意图

**协同设计**：企业级协同（150 人协作、多项目并行、角色权限、任务分配）、内置"榜豆 AI"智能助手（解答操作问题/解读速查报告/定位短板）。

### 2.3 GEO 设计思想（行业共识）

1. **核心转变：从"被搜索"到"被理解、被引用、被信任"**——"AI 不'找'内容，而是'读'内容"，内容的终极受众从人类变为 AI 模型。SEO 解决"被搜索"（排名/流量），GEO 解决"被 AI 优先引用"（认知占领）。
2. **GEO 价值金字塔**：精准性（语义建模提升意图识别）→ 实时性（内容与 AI 索引同步更新）→ 可解释性（让 AI 验证逻辑与数据来源）→ 防御性（语义防御，防 AI 误读/混淆品牌）。
3. **内容四项原则**：观点有深度、数据可验证、来源具权威——适配大模型"检索-证据选取-生成-引用"机制。
4. **典型四步走流程**：策略制定（分析目标用户会向 AI 提什么问题）→ 问题库构建（批量生成相近问题）→ 内容优化（生成对应标准答案）→ 分发与监测（持续监测 AI 引用并迭代）。与摘星五部曲互补。
5. **从"被收录"到"被引用"的两阶段进阶**：入门=被 AI 收录（指标：品牌提及率、引用率）；进阶=被 AI 优先引用（指标：**首选引用率、答案占比**）。
6. **"可引用素材"结构**：AI 更青睐"结论前置、观点独立成段、数据标注来源、段落有明确小标题"的内容——这是内容生成的模板依据。
7. **认知主权/语义场**：品牌必须掌握"被 AI 正确理解"的能力，用"主题包围战"（品牌语义场设计 + 内容矩阵规划）占领心智。

## 五、整洁架构归位设计（v3 新增）

### 5.1 核心诊断：问题不是"忘了写代码"，而是"业务规则住错了层"

对 4.2/4.3 逐条套用整洁架构的分层判定（依赖向内 / 变化速率不同处画边界），会发现它们共享同一根因：**表达层（前端）先行生长，而每条业务规则归属哪一层从未定论**。v2 规划回答了"页面长什么样"，没有回答"规则住在哪一层"——于是：

- 健康分合成（五指数+权重+竞品差距）是典型的**应用级业务规则**（用例层），却写在了最外层的前端 `geoHealth.ts`。同一规则被三处以不同入参调用 → 口径不一；每个页面各自拉全量数据重算 → N+1（Home 逐品牌 `listContents`）与性能恶化；换客户端（App/小程序）就要重写一遍规则。
- 监测结果组装在 `Monitor`/`MonitorKeyword`/`MonitorMultiEngine` 三条路径各自手工搬运字段 → 新增字段时"改一处漏两处"（信源字段断流 ① 即由此而来）。
- API 视图是手工 `gin.H` 白名单（map 无编译期字段检查）→ 实体加字段它不知道，断裂静默发生；前端 `types/api.ts` 又是另一份手工翻译 → 契约漂移，"虚必填"让 TS 编译器反成错误安全感的来源。
- 一个 `llmConfigToView` 服务于两个用例（商户"我有哪些引擎" vs 管理员"配置厂商密钥"）→ 视图未按用例分离，密钥泄露给商户（缺陷 ④）。

> 整洁架构检验标准："换 UI / 换客户端，业务核心要不要改？"——当前健康分、竞品聚合、情感分布口径全部在前端，答案是"要改"。这就是口径漂移与数据断流的架构级解释。

**分层归位表**（每条规则一个唯一归属，跨处引用其输出而非复制其逻辑）：

| 业务规则 | 归属层 | 现状位置 | 归位后 |
|---|---|---|---|
| GEO 健康分合成（五指数+权重+环比） | 用例层 | 前端 `geoHealth.ts` | Go `geo.HealthReport` 用例，单一事实源 |
| 竞品对标聚合（自家 vs 竞品+威胁榜+情感对比） | 用例层 | 前端 `competitorStats` | 并入 `HealthReport` 输出 |
| 首选提及率 | 实体（计数地基）+用例（比率） | 前端 `avg_position===1` 近似 | 实体加 `FirstPickCount`，用例输出 `first_pick_rate` |
| 监测结果组装（字段搬运） | 用例层私有构造函数 | 三条监测路径各自手工 | 单一 `newMonitoringResult(probe, …)`，三路径共用（DRY 收敛点） |
| API 视图序列化 | 接口适配器 | 手工 `gin.H` 白名单 | typed struct（编译期字段检查）+ 契约守护测试 |
| 引擎名单 / 厂商密钥配置 | 两个用例、两个 Output Model | 一个视图服务两端 | 商户端 `ListEngineNames`（仅 name）；完整视图仅 admin 路由可达 |
| 跨品牌趋势序列（驾驶舱 ViewModel） | 用例层输出形状 | 前端 `byKey` 自拼（缺陷 ② 源头） | 聚合用例直接输出降采样时间序列（含 brand_id/name，已排序，按天/按周参数化） |
| 情感枚举合法性 | 实体层 | LLM 任意字符串透传落库 | 实体构造校验 ∈ {positive, neutral, negative, ""}，非法归一 neutral |

### 5.2 修复设计（自内向外，按层）

**实体层（internal/domain/entity）**
- `MonitoringResult` 增加 `FirstPickCount int`（被提及且位次=1 的采样数）。迁移 `045_monitoring_result_first_pick.sql`：`INT NOT NULL DEFAULT 0`，旧数据缺省 0——与 sentiment 的存量兼容模式一致。
- 情感枚举校验：实体构造/赋值处归一非法值（自家与竞品同口径）。
- `AIRankProbeItem.AvgPos` 二选一：复用 `analyzeMention` 的位次提取真正赋值，或删除该占位字段——占位字段是导航噪音。

**用例层（internal/usecase/geo）**
- 新增 `HealthReport(ctx, tenantID)` 用例：一次仓储查询聚合五指数+总分+竞品差距+环比+降采样趋势序列。这是 v2 路线图"聚合端点"的落地，同时消解四类问题：前端三处口径、Home 的 N+1、趋势拼装（缺陷 ② 从根上消除而非修补）、trend 排序假设。`RankUseCase.Overview`（`monitor.go:442`）只聚合提及率的现状在此扩展。
- 监测结果组装收敛为单一构造函数（三条监测路径共用）——"改一处漏两处"从结构上消除，缺陷 ① 的用例侧不再复发。
- 情感聚合口径统一：自家与竞品均多数投票；降级路径（fallbackStringMatch）通过 `Confidence` 下降 + 显式 `semantic_degraded` 标记可见，不再静默失真。
- 测试补齐：`AIEngineProbe` 已是 port（`port/geo_engine.go:114`），补 in-memory mock 即可离线测试（谦卑对象模式：probe adapter 只搬运，`matchBrandFromList`/投票合成/位次均值等纯函数直接表驱动测试）——结束 `monitor.go` 零测试状态。

**接口适配器层（internal/adapter/handler）**
- `monitoringResultToView` 补 `sources`/`self_source_count`/`first_pick_count`，并由 `gin.H` 换 typed struct——map 无编译期字段检查是缺陷 ① 不可见的直接原因。
- 新增商户端引擎名单端点（`GET /geo/engines` → `[]string`，挂 `router_geo.go`）；含 `api_key` 的完整视图仅 admin 路由可达——缺陷 ④ 关闭。
- 契约守护：一个反射测试断言"实体公开字段 ⊆ 视图 struct 字段"，防止再次静默断流；前端 `types/api.ts` 对应字段改为可选+显式兜底语义。

**前端（展示层归位：只做展示与交互，不再持有业务规则）**
- `geoHealth.ts` 的 `computeHealth`/`competitorStats` 改为消费后端 `HealthReport`；文件保留为接口降级期兜底（404 时本地重算），灰度后退役。
- OverviewTab 趋势/排行直接消费聚合输出；`byKey` 拼装、下标对齐、trend 排序假设三类代码删除。
- QuickCheck 历史：合并为单 effect+函数式更新+按 id 去重截断 5 条（缺陷 ③）。
- 速查完成后 `invalidateQueries(['geo-monitor-results','geo-overviews','geo-advice-last'])`。
- 批量监测/批量加词：`Promise.allSettled` 受控并发（并发度 3）+部分失败汇总提示。
- CSV 转义（引号包裹+双引号转义+`=`/`+`/`-`/`@` 公式前缀防护）。
- 竞品 Tag 移除失败回滚（先备份、catch 恢复+提示）；「提及率 {s.address}」语义错位改为显示 `rating` 占比。
- 问题词 intent 由蒸馏源头带出（`questions` source 返回意图分布并随词入库），前端三处硬编码删除。

1. **能力层已对齐甚至超越行业多数产品**（多引擎采样矩阵、RAG 内容生成、公开站信源、RPA 分发、引用归因），缺口集中在**表达层**与**语义层**：缺健康总分、缺情感维度、缺位次、缺竞品对标、缺信源分类、缺时间维度、缺站点审计。
2. **v2 最重要的认知升级**：行业驾驶舱 = 提及率 + **情感倾向** + **竞品对比**（摘星"语义份额驾驶舱"、Geowise 订阅追踪、万象镜五指数的共同构成）——情感/位次数据扩展应作为 P0，而不是 P2。
3. 摘星五部曲 / GEO 四步走与现有功能一一对应，界面应按闭环流程组织心智；"从被收录到被引用"的两阶段指标是效果叙事的最佳框架。
4. 本规划全部为前端重构 + 监测数据结构增量 + 少量聚合端点，无数据库/架构层改动，可分批落地。（v3 修订：A1/A2 阶段引入用例层与适配器层改动，见第五章——原表述仅适用于 v2 的 P0-P2 前端部分）
5. **v3 审计结论**：v2 的 P0/P1 主体与部分 P2 已落地，且情感/位次探测有两处超规划设计（防确认偏误、解析/被测引擎分离）；新的主要风险从"缺功能"转为"业务规则住错层"——健康分/竞品聚合在前端、视图序列化无守护、监测组装三路径重复。
6. **v3 归位原则**（整洁架构）：一条业务规则一个唯一归属层，跨处引用其输出而非复制其逻辑；实体演化必须带契约守护（typed struct + 反射测试），否则"信源断流"这类静默断裂必然复发；页面布局（第六章）只做表达，口径与聚合一律来自用例层输出。
