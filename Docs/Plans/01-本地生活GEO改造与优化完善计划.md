### X-01 收口明细（商业闭环：收入 vs 成本双报表）

1. **配额语义修正（关键缺陷修复）**：配额计数 = usages 记录数（每次 LLM 调用一条），旧配额 monitor=30/500 按"批次"理解，实际 1 次全量监测 ≈ 300 条——免费用户连一次完整监测都做不了。已按"LLM 调用次数"语义重设计：free monitor=500（≈50 次单关键词监测）、pro=8000（≈27 次全量）、team 无限；新增 nearby/diagnose 场景配额。
2. **兼容升级**：`SeedPlans` 改为"补齐缺失场景"——已部署库自动获得 nearby/diagnose 配额，运营修改过的场景值不被覆盖（旧 monitor 值需 admin 按新语义手动调整）。
3. **新场景计量**：`NearbyUseCase`（nearby 配额 + 业务动作计数，非 LLM 调用 TotalTokens=0）、`DiagnoseUseCase`（diagnose 配额 + WithUsageContext 计量）——超限统一 402。
4. **成本分析端点**：`GET /admin/billing/cost-analysis`（近 N 天按场景：调用次数/tokens/估算成本）；参考单价 `LLM_COST_PER_MToken`（默认 ¥1/百万 tokens，运营按实际模型配置）——与既有 `RevenueReport` 组成"收入 vs 成本"双报表。
5. **前端**：套餐页配额换算提示（"1 次监测 ≈ 10 次调用"）、内容卡片"被引用 N 次"。

**新增端点（本轮）**：`GET /admin/billing/cost-analysis`、`GET /geo/brands/:id/citations`
**新增配置**：`LLM_COST_PER_MToken`（默认 100 = ¥1/百万 tokens）
**测试新增**：配额语义断言、SeedPlans 兼容升级（运营值保留 + 新场景补齐）、CostAnalysis 三态、CitationUseCase 归因计数

## 二、老板三个想法的可行性评估

### 2.1 想法① 对接位置 API（获取使用地址→定位）

| 维度 | 评估 |
|---|---|
| 可行性 | 🟢 **高可行**。国内三选一：高德/百度/腾讯地图 Web 服务 API，Go SDK 成熟，免费额度充足（高德个人 KEY 地理编码日配额 5000 次，SaaS 初期够用） |
| 落点 | `port.GeoLocator` 接口 + `adapter/geo/amap.go` 实现（地理编码/逆地理编码/行政区划解析），未配 KEY 时 mock 降级（沿用项目双实现惯例） |
| 边界与修正 | ⚠️ **不要存"老板手机实时定位"**——应存"店铺地址→地理编码结果"（老板主动填写地址，隐私负担小、数据稳定）。若做浏览器 Geolocation 自动获取，需授权弹窗 + 明确告知用途（个人信息保护法合规） |
| 衍生价值 | 地址/经纬度是后面所有本地功能的**地基**：周边搜索中心点、发布定位、地图卡片、LocalBusiness JSON-LD 全部依赖它 |

### 2.2 想法② 附近同行业门店对比排名

| 维度 | 评估 |
|---|---|
| 可行性 | 🟢 **方向可行，但实现路径要修正** |
| ❌ 修正点 | **"用搜索引擎查询附近门店"不建议**——搜索引的本地结果依赖地图数据、无结构化 API、爬取有合规与稳定性风险。**改为地图 POI 周边搜索 API**（高德"周边搜索"：中心点+关键词+半径，返回门店名/地址/距离/经纬度/评分(部分覆盖)/营业状态），数据真实、一次一查、按需展示 |
| 落点 | `port.POISearcher.SearchNearby(ctx, center, keyword, radius)` + `adapter/geo/amap_poi.go`；`usecase/geo/nearby.go` 新用例：品牌门店位置 → 行业品类词 → POI 搜索 → 与手动竞品清单 + AI 竞品提及率合并 → **双榜对照视图**（真实地图榜 + AI 提及榜） |
| 合规 | POI 按需查询、聚合展示（非批量抓取转售）在服务条款下一般可行；**任务前置：核实高德商业授权条款**（涉及付费客户使用需确认授权等级） |
| 商业价值 | 这是把"相对位置"从 AI 虚拟世界带到现实世界——**"你店 500 米内 3 家川菜馆评分都比你高 0.5" 比 "AI 提及率 30%" 更能让老板掏钱** |

### 2.3 想法③ 视频/内容附地址 → 附近搜索曝光

| 维度 | 评估 |
|---|---|
| 可行性 | 🟢 内容层**高可行**；平台层 ⚠️ **有资质门槛，需分层规划** |
| 内容层（✅ 简单先做） | 生成文章/视频文案自动附加"📍 地址：XX区XX路X号"；公开文章页增加地址信息块 + **LocalBusiness/Restaurant JSON-LD**（对本地搜索是真实排名信号，现固定 Article 类型未利用）；Vidu 提示词模板支持文本场景时叠加地址字幕 |
| 平台层（⚠️ 探路） | 抖音 POI 挂载需要**抖音来客/企业号 + 本地生活服务商资质**，开放 API 不对个人开放——这是资质问题不是技术问题。务实路径：① RPA 发布（现有 `auto_channel.go`）尝试模拟"添加定位"（先人工验证可行性，视频+定位是平台风控重点区，做好随时失效准备）；② 半自动引导：发布页一键复制"文案+地址"，老板手动选定位（最稳） |
| 落点 | 发布任务/视频任务输入扩展 `storeAddress` 字段；发布通道 `PublishInput` 增加 `Location` 参数；前端发布页显示地址选择/复制 |

### 2.4 三个想法综合结论

> **方向全部正确，正好补上 P0 缺口**：①补"无位置维度"，②补"无真实世界基准"，③补"本地曝光转化"。需修正两处：②用地图 POI API 而非搜索引擎；③先内容层后平台层（资质探路）。
> 三者有强依赖顺序：**①是②③的地基**，必须先做。

## 七、P4 探路结论：抖音/小红书"添加定位"（2026-08-11 调研）

### 7.1 结论一句话

> **内容层先做（已上线：发布正文附"📍 地址" + 分发中心定位指引）；平台层自动定位暂缓——抖音 POI 挂载是"资质问题 + 风控问题"，不是纯技术问题。**

### 7.2 调研要点

| 路径 | 可行性 | 说明 |
|---|---|---|
| **抖音本地生活官方 API** | ⚠️ 资质门槛 | 抖音来客/生活服务开放平台：POI 挂载、团购、视频挂载需要**企业认证 + 本地生活服务商资质**，个人/普通商户不可直接调用；SaaS 若代运营需签约服务商协议 |
| **抖音开放平台视频发布** | ⚠️ 门槛 | 视频发布接口仅对认证企业号/机构开放，个人开发者无发布权限；且视频挂 POI 需本地生活权限包 |
| **小红书笔记定位** | 🟡 半可行 | 小红书创作平台笔记"添加地点"仅部分账号（企业号/专业号）开放；个人号定位能力不完整 |
| **RPA 模拟（现有 chromedp 通道）** | 🟡 高风险实验 | 技术可行（发布页点定位 → 搜索地址 → 选中），但**视频+定位是平台风控重点区**：发布频控、设备指纹、异地登录触发。必须多账号轮换 + 低频率 + 人工验证 |
| **半自动引导（已上线）** | ✅ **最稳** | 发布正文已自动带地址行；分发中心提供"手动添加定位"操作指引——0 风控风险，老板 30 秒完成 |

### 7.3 决策与下一步（探路任务）

1. ✅ **P4-03 半自动兜底已上线**：分发中心"定位操作指引"卡片。
2. ✅ **P4-01 代码已标记**：`adapter/publisher/auto_channel.go` 头部注释记录定位步骤实现路径（地址来自 `job.StoreAddress`，字段已就位，业务零改动）。
3. ⏸️ **P4-02 实施决策**：优先做「人工验证实验」（执行清单见 7.4），数据支持后再写自动步骤。同时评估"抖音来客服务商"合作模式（投入产出比）。

### 7.4 人工验证实验执行清单（P4-01 前置探路）

> 目标：用**手动流程**（非自动脚本）验证"发布内容 + 添加定位"在抖音/小红书的可行性与风控表现，为 RPA 自动定位步骤的取舍提供数据。

**前置条件**
- [ ] 1 个抖音内测账号（**非主运营账号**——实验有封号风险）+ 1 个小号（备用）
- [ ] 门店档案已建且地理编码成功（`/m/nearby` 门店状态 = 已定位）
- [ ] 至少 1 篇已发布内容（`/m/content` 状态 = 已发布）

**执行步骤（每篇内容重复，共 10 次，间隔 ≥ 24 小时）**
1. [ ] 分发中心选择内容 → 半自动发布（预填草稿页）或手动复制文案（含"📍 门店地址"行）
2. [ ] 发布页点击"添加定位/地点"→ 搜索门店地址 → 选中门店 POI
3. [ ] 发布，**逐次记录**下表：
4. [ ] 每次发布后 2 小时 + 24 小时检查：内容是否被限流（仅自己可见）、是否被删除、账号是否有异常提醒

**记录表（每次一行）**

| # | 日期 | 平台 | 内容类型(图文/视频) | 定位是否成功 | 发布是否成功 | 2h 后可见性 | 24h 后可见性 | 账号异常 | 备注 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | | 抖音 | | | | | | | |
| 2 | | | | | | | | | |
| …（共 10 行）|

**判定标准（10 次后）**
- ✅ **可自动化的信号**：≥8 次定位成功 + 0 次限流/删除/封号 → 在 `auto_channel.go` 写自动定位步骤（先灰度：单账号每周 ≤3 次）
- ⚠️ **半自动优先的信号**：定位成功率 <8 次 或 出现 1-2 次限流 → 保持半自动指引，不写自动步骤
- 🔴 **放弃自动化的信号**：出现封号/多次限流（≥3 次）→ 永久放弃 RPA 定位，只保留内容层地址 + 半自动指引；评估抖音来客官方通道

**合规红线**
- [ ] 实验期间不使用自动脚本（人工操作，模拟真实用户）
- [ ] 不批量/高频发布（间隔 ≥24h）
