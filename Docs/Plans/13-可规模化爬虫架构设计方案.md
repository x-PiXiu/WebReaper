> 日期：2026-08-24 | 状态：待开发 | 优先级：P1

## 零、核心架构决策：平台方统一爬取

> **关键设计**：用户不需要登录即可查看灵感数据。只有发布内容时才需要用户登录自己的账号。

### 0.1 两种模式对比

```
模式 A：每用户各自爬取（❌ 不采用）
  用户 A 扫码登录 → 用 A 的 Cookie 爬取川菜热门 → A 看自己的数据
  用户 B 扫码登录 → 用 B 的 Cookie 爬取火锅热门 → B 看自己的数据
  问题：
    - 每个用户都要扫码，体验差
    - 每个用户的 Cookie 都要管理，复杂度高
    - 每个用户都要消耗爬虫资源
    - 用户数量 × 平台数 = Cookie 数量爆炸

模式 B：平台方统一爬取（✅ 采用）
  平台方账号（管理员）→ 分时段爬取各品牌热门数据 → 存入 DB
  用户 A 打开灵感广场 → 直接看 DB 数据（无需登录）
  用户 B 打开灵感广场 → 直接看 DB 数据（无需登录）
  用户要发布内容时 → 才需要扫码登录自己的账号
  优势：
    - 用户零门槛，打开就看
    - 只管理几个平台方账号
    - 统一调度，资源可控
    - 代理轮换集中管理

  ⚠️ 关键细节：不是一次性爬取所有品牌，而是分时段轮流爬取
  06:00 → 爬取品牌 A（川菜）
  06:15 → 爬取品牌 B（火锅）
  06:30 → 爬取品牌 C（奶茶）
  ...
  12:00 → 第二轮：品牌 A 刷新
  12:15 → 第二轮：品牌 B 刷新
  ...
  好处：
    - 每个品牌的请求分散在时间线上，不会集中爆发
    - 单个账号的请求频率可控（每 15 分钟一个品牌）
    - 某个品牌爬取失败不影响其他品牌
    - 新增品牌只需加入队列，不影响现有节奏
```

### 0.3 对架构的影响

| 组件 | 原设计 | 新设计 |
|------|--------|--------|
| **Cookie 来源** | 每用户各自的 Cookie | 平台方账号的 Cookie（管理员维护） |
| **爬虫触发** | 用户首次打开时触发 | 定时任务自动触发（与用户无关） |
| **用户登录** | 查看灵感也需要登录 | 只有发布才需要登录 |
| **账号管理** | 用户自己管理 | 管理后台统一管理 |
| **代理策略** | 每用户独立代理 | 平台方账号独立代理（集中管理） |
| **数据归属** | 按用户隔离 | 全局共享（按品牌筛选） |

### 0.4 平台方账号管理

```sql
-- 平台方账号表（管理员维护，用于数据爬取）
CREATE TABLE IF NOT EXISTS crawler_accounts (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    platform VARCHAR(32) NOT NULL,           -- douyin/kuaishou/bilibili
    account_name VARCHAR(128) NOT NULL,      -- 账号名称（管理员备注）
    cookie_encrypted TEXT NOT NULL,           -- AES-256-GCM 加密的 Cookie
    user_agent VARCHAR(512) NOT NULL DEFAULT '',
    proxy_address VARCHAR(256) NOT NULL DEFAULT '',  -- 专属代理地址
    status VARCHAR(16) NOT NULL DEFAULT 'active',    -- active/expired/banned
    last_used_at DATETIME(3) NULL,
    last_health_check_at DATETIME(3) NULL,
    health_check_result VARCHAR(16) NOT NULL DEFAULT 'unknown', -- healthy/unhealthy
    daily_usage_count INT NOT NULL DEFAULT 0,  -- 当日使用次数
    daily_usage_limit INT NOT NULL DEFAULT 50, -- 每日使用上限
    created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
    INDEX idx_platform_status (platform, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 0.5 账号轮换策略

```
每次爬取任务：
  1. 从 crawler_accounts 选择一个可用账号
     - status = 'active'
     - health_check_result = 'healthy'
     - daily_usage_count < daily_usage_limit
     - 优先选择使用次数最少的账号（负载均衡）
  2. 使用该账号的 Cookie + 代理发起请求
  3. 请求成功：daily_usage_count++
  4. 请求失败（风控）：标记 status = 'banned'，切换下一个账号
  5. 每日 0 点重置 daily_usage_count

定时健康检查（每 30 分钟）：
  - 对每个 active 账号发一个轻量请求（如访问首页）
  - 成功：health_check_result = 'healthy'
  - 失败/重定向到登录：health_check_result = 'unhealthy'
```

## 一、MediaCrawler 设计思想提炼

### 1.1 核心设计哲学

MediaCrawler 的成功不在于它写了多少平台爬虫，而在于它的**架构让新增平台的成本极低**。提炼出 6 个核心设计思想：

| # | 设计思想 | MediaCrawler 实现 | WebReaper 借鉴 |
|---|----------|-------------------|----------------|
| 1 | **抽象工厂 + 策略模式** | `AbstractCrawler` → 7 个平台实现 | `CrawlerPlatform` 接口 → 多平台 |
| 2 | **接口归内层，实现在外层** | `base/` 定义接口，`media_platform/` 实现 | `usecase/port` 定义接口，`adapter/` 实现 |
| 3 | **配置驱动行为** | `base_config.py` + 平台 config | DB 驱动的 `crawler_configs` 表 |
| 4 | **反爬是一等公民** | CDP/stealth/签名/代理/限速 五层防护 | CDP + 限速 + Cookie 管理 |
| 5 | **存储可插拔** | 8 种存储后端，Factory 选择 | 统一 `InspirationRepository` |
| 6 | **渐进式降级** | API 失败 → 浏览器降级 → 通用搜索兜底 | 同样的降级链路 |

### 1.2 MediaCrawler 的爬虫编写模式

每个平台爬虫由 5 个文件组成（统一模式）：

```
media_platform/douyin/
├── core.py      ← 主爬虫（编排整个流程）
├── client.py    ← API 客户端（HTTP 请求 + 签名）
├── login.py     ← 登录策略（二维码/手机/Cookie）
├── field.py     ← 枚举常量（搜索频道、排序、时间过滤）
└── help.py      ← 工具函数（URL 解析、签名辅助）
```

**关键洞察**：`core.py` 是编排者，`client.py` 是执行者。core 不关心 HTTP 细节，client 不关心业务流程。这种分离让每个平台的"怎么搜"和"搜什么"解耦。

### 1.3 WebReaper 的优势

WebReaper 已经有了 MediaCrawler 的核心骨架：

| MediaCrawler | WebReaper 现有 | 差距 |
|---|---|---|
| `AbstractCrawler` | `port.SocialSearcher` | ✅ 接口已定义 |
| `media_platform/douyin/` | `adapter/douyinweb/` | ✅ 抖音已实现 |
| `base_config.py` | `config/base_config.py` | ⚠️ 缺少爬虫动态配置 |
| CDP 模式 | chromedp | ⚠️ 需升级为 CDP 连接真实浏览器 |
| 7 个平台 | 1 个平台（抖音） | ⚠️ 需加快手、B站 |
| Admin 控制 | 无 | ❌ 需新建 |

### 1.4 MediaCrawler 核心爬取机制深度分析

> **关键发现：MediaCrawler 不是用浏览器爬取页面，而是用浏览器获取 Cookie，然后直接调用平台 API。**

#### 三种爬取方式对比

| 方式 | 原理 | 代表 | 反爬效果 | 速度 |
|------|------|------|----------|------|
| **A. 浏览器渲染爬取** | 浏览器打开页面 → 解析 DOM → 提取数据 | Scrapy+Selenium | ⭐⭐ 最弱 | 最慢 |
| **B. 页面内 XHR 爬取** | 浏览器打开页面 → 在页面内执行 XHR → 拿到 JSON | WebReaper 现有方案 | ⭐⭐⭐ 中等 | 中等 |
| **C. API 直接调用** | 浏览器只拿 Cookie → httpx 直接调 API → 签名算法绕过 | MediaCrawler | ⭐⭐⭐⭐⭐ 最强 | 最快 |

#### MediaCrawler 的真实流程

```
┌─────────────────────────────────────────────────────────────┐
│  浏览器（Playwright/CDP）—— 仅用于登录和 Cookie 获取         │
│                                                              │
│  1. 打开 douyin.com                                          │
│  2. 用户扫码/输入手机号登录                                    │
│  3. 登录成功后，提取 Cookie（document.cookie）                 │
│  4. 提取 User-Agent（navigator.userAgent）                    │
│  5. 提取 msToken（window.localStorage）                       │
│  6. 关闭浏览器（或保持连接用于签名）                            │
└──────────────────────────┬──────────────────────────────────┘
                           │ Cookie + UA + msToken
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  API 客户端（httpx）—— 真正的数据获取                         │
│                                                              │
│  1. 构造请求参数（keyword, offset, count, 设备指纹...）        │
│  2. 调用签名算法生成 a_bogus 参数                              │
│  3. httpx GET https://www.douyin.com/aweme/v1/web/...       │
│  4. 解析 JSON 响应 → 结构化数据                               │
└─────────────────────────────────────────────────────────────┘
```

#### 核心思想总结

MediaCrawler 的核心思想是**把浏览器的用途压缩到最小**：

| 用途 | 是否需要浏览器 | 替代方案 |
|------|---------------|----------|
| 登录（扫码/手机） | ✅ 必须 | 无替代 |
| Cookie 提取 | ✅ 必须 | 无替代 |
| msToken 提取 | ✅ 必须 | 无替代 |
| 签名算法执行 | ❌ 不需要 | execjs / 纯算法库 |
| API 调用 | ❌ 不需要 | httpx 直接调用 |
| 数据解析 | ❌ 不需要 | JSON 解析 |

**浏览器只做"身份验证"，所有数据获取都走 HTTP API。这是 MediaCrawler 速度快、反爬强的根本原因。**

#### 降级策略（各平台自实现，非统一架构）

> **源码验证**：降级不是统一的架构模式，而是各平台根据自身特点独立实现的。

| 平台 | 降级策略 | 源码位置 |
|------|----------|----------|
| **小红书** | API 失败 → HTML 解析（最复杂） | `xhs/core.py` 第 308-315 行：`try get_note_by_id()` → `except RetryError` → `get_note_by_id_from_html()` |
| **快手** | 指数退避重试 + 20 秒冷却 + Cookie 刷新 | `kuaishou/client.py` 第 126-158 行：`for attempt in range(3): delay = 5 * (2**attempt)` |
| **B站** | 评论级重试 + 指数退避 | `bilibili/client.py` 第 291-307 行：`max_retries=3, delay=5*(2**attempt)` |
| **抖音** | 最简单，失败直接 break | `douyin/core.py` 第 155-157 行：`except DataFetchError: break` |
| **所有平台** | CDP 模式失败 → 标准 Playwright 模式 | 各平台 `core.py` 的 `launch_browser_with_cdp()` 方法 |

**对 WebReaper 的启示**：降级策略应该按平台特点独立实现，不要强求统一。抖音搜索不需要签名所以降级简单，小红书有 HTML 解析兜底所以降级复杂。

#### 配置系统（可变模块级变量，支持运行时修改）

> **源码验证**：MediaCrawler 的配置不是不可变对象，而是 Python 模块级变量，支持运行时修改。

```python
# config/base_config.py — 模块级变量
CRAWLER_MAX_NOTES_COUNT = 15  # 默认值

# douyin/core.py 第 131 行 — 运行时修改
if config.CRAWLER_MAX_NOTES_COUNT < dy_limit_count:
    config.CRAWLER_MAX_NOTES_COUNT = dy_limit_count  # 运行时覆盖
```

**对 WebReaper 的启示**：配置系统应该支持两种模式：
1. **DB 驱动**（管理后台可改）：`crawler_configs` 表存储配置，定时任务读取
2. **运行时覆盖**：某些配置（如单次搜索数量）可以在代码中动态调整

## 二、架构设计

### 2.1 核心数据流（参考 MediaCrawler）

> **关键设计思想：浏览器只负责"身份"，httpx 负责"数据"。**

```
┌─────────────────────────────────────────────────────────────┐
│  阶段 1：浏览器（Playwright/CDP）—— 仅用于身份获取            │
│                                                              │
│  1. 连接用户 Chrome（CDP）或启动内置 Chromium                  │
│  2. 导航到平台首页，等待用户登录（扫码/手机号/Cookie）           │
│  3. 登录成功后，提取：                                        │
│     - Cookie（document.cookie）                              │
│     - User-Agent（navigator.userAgent）                      │
│     - msToken（window.localStorage）                         │
│  4. 保持页面打开（msToken 需要实时读取）                        │
│                                                              │
│  ⚠️ 浏览器不做：不导航到搜索页，不解析 DOM，不执行 XHR          │
└──────────────────────────┬──────────────────────────────────┘
                           │ Cookie + UA + msToken
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  阶段 2：API 客户端（httpx）—— 真正的数据获取                  │
│                                                              │
│  1. 构造请求参数（keyword, offset, count, 设备指纹...）        │
│  2. 调用签名算法生成签名参数                                   │
│     - 抖音：execjs 执行 douyin.js → a_bogus                   │
│     - 小红书：xhshow 纯算法库 → x-s/x-t/x-s-common           │
│     - B站：wbi 签名（纯 Go 实现）                              │
│  3. httpx GET/POST 平台 API 端点                              │
│  4. 解析 JSON 响应 → 结构化数据                               │
│                                                              │
│  ✅ 优势：毫秒级请求，无需等待页面渲染                          │
└─────────────────────────────────────────────────────────────┘
```

#### `port.CrawlerPlatform` — 平台爬虫接口

```go
// CrawlerPlatform 社交媒体平台爬虫接口。
//
// 设计（策略模式）：每个平台实现此接口，用例层通过平台名动态选择。
// 新增平台 = 新增 adapter 实现 + 注册一行，用例零改动。
//
// 内部分工（参考 MediaCrawler core.py + client.py 分离模式）：
//   - Crawler 实现本接口（编排：搜索循环、分页、去重、排序）
//   - Client 是 Crawler 的内部组件（执行：httpx 请求、签名、代理轮换）
type CrawlerPlatform interface {
    // Platform 返回平台标识（"douyin"/"kuaishou"/"bilibili"）。
    Platform() string

    // Search 关键词搜索热门视频。
    // 内部流程：构造参数 → 签名 → httpx 调 API → 解析 JSON → 去重排序
    Search(ctx context.Context, opts SearchOptions) ([]CrawledVideo, error)

    // GetDetail 获取单个视频详情（含完整互动数据）。
    GetDetail(ctx context.Context, videoID string) (*CrawledVideo, error)

    // RefreshMetrics 批量刷新视频的实时指标（播放量/点赞/评论等）。
    RefreshMetrics(ctx context.Context, videoIDs []string) ([]MetricsUpdate, error)

    // IsAlive 检测平台连接是否正常（Cookie 有效性）。
    IsAlive(ctx context.Context) bool

    // GetCapabilities 返回平台支持的能力（搜索/详情/评论/刷新）。
    GetCapabilities() PlatformCapabilities
}

// CrawlerClient 平台 API 客户端接口（Crawler 的内部组件）。
//
// 设计（参考 MediaCrawler AbstractApiClient）：
//   - 每个平台实现此接口，负责 HTTP 请求细节
//   - Crawler 通过此接口调用平台 API，不直接处理 HTTP
//   - 职责：签名生成、代理轮换、分页循环、回调处理
type CrawlerClient interface {
    // Search 发起搜索 API 请求（单次，不含分页循环）。
    Search(ctx context.Context, keyword string, offset int, limit int) (*SearchResponse, error)

    // GetDetail 发起视频详情 API 请求。
    GetDetail(ctx context.Context, videoID string) (*CrawledVideo, error)

    // GetComments 发起评论 API 请求（支持分页）。
    GetComments(ctx context.Context, videoID string, cursor string, limit int) (*CommentResponse, error)

    // UpdateCookies 从浏览器上下文提取并更新 Cookie。
    UpdateCookies(ctx context.Context, browser *BrowserContext) error

    // IsAlive 检测 Cookie 是否有效。
    IsAlive(ctx context.Context) bool
}
```

### 2.4 CDP 浏览器管理器（三级降级策略）

```go
// CDPBrowserManager Chrome DevTools Protocol 浏览器管理器。
//
// 设计动机（参考 MediaCrawler 的 CDP 模式）：
//   - 浏览器仅用于登录和 Cookie 提取，不用于数据爬取
//   - 三级降级：用户 Chrome → 用户 Edge → 内置 Chromium
//   - 管理多个平台的 Cookie 注入/提取
//   - 复用浏览器上下文，避免每次搜索都开新浏览器
type CDPBrowserManager struct {
    debugPort  int
    mode       string // "auto" / "cdp" / "builtin"
    mu         sync.Mutex
    contexts   map[string]*rod.Browser // platform → browser instance
    cookies    map[string][]*http.Cookie // platform → cookies
}

// Connect 三级降级连接浏览器。
//
// 优先级 1: CDP 连接用户已运行的 Chrome（端口 9222）——反爬最强
// 优先级 2: CDP 连接用户已运行的 Edge（Edge 也支持 CDP，基于 Chromium）
// 优先级 3: 自动下载并启动内置 Chromium + stealth 注入——兜底方案
func (m *CDPBrowserManager) Connect(ctx context.Context, platform string) (*rod.Browser, error) {
    // 优先级 1: 用户 Chrome
    if b, err := m.connectCDP(platform, "chrome"); err == nil {
        return b, nil
    }
    // 优先级 2: 用户 Edge
    if b, err := m.connectCDP(platform, "edge"); err == nil {
        return b, nil
    }
    // 优先级 3: 内置 Chromium
    return m.launchBuiltin(platform)
}

// connectCDP 尝试连接已运行的浏览器实例。
func (m *CDPBrowserManager) connectCDP(platform, browserType string) (*rod.Browser, error)

// launchBuiltin 启动内置 Chromium + stealth 注入。
func (m *CDPBrowserManager) launchBuiltin(platform string) (*rod.Browser, error)

// InjectCookies 向浏览器注入 Cookie。
func (m *CDPBrowserManager) InjectCookies(ctx context.Context, platform string, cookies []*http.Cookie) error

// ExtractCookies 从浏览器提取当前 Cookie。
func (m *CDPBrowserManager) ExtractCookies(ctx context.Context, platform string) ([]*http.Cookie, error)

// Close 关闭浏览器连接。
func (m *CDPBrowserManager) Close(platform string)
```

#### 浏览器模式对比

| 模式 | 用户操作 | 反爬效果 | 适用场景 |
|------|----------|----------|----------|
| CDP + 用户 Chrome | 先手动打开 Chrome | ⭐⭐⭐⭐⭐ 最强 | 重度使用，长期运行 |
| CDP + 用户 Edge | 先手动打开 Edge | ⭐⭐⭐⭐⭐ 同样强 | 没装 Chrome 的用户 |
| 内置 Chromium | 无需任何操作 | ⭐⭐⭐ 一般 | 兜底，首次体验/服务器部署 |

**签名方案**（三种选择，按优先级）：

| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| A. execjs 执行 JS | 从 MediaCrawler 复制 `douyin.js`，Go 调用 Node.js | 签名准确 | 依赖 Node.js |
| B. 纯 Go 实现 | 逆向 a_bogus 算法，Go 重写 | 无外部依赖 | 维护成本高 |
| C. 页面内 XHR 降级 | 打开搜索页，在页面内执行同步 XHR | 不需要签名 | 速度慢（8 秒/次） |

**建议**：方案 A 为主，方案 C 为降级。参考 MediaCrawler 的 `help.py`：

```python
# MediaCrawler 签名实现（help.py 第 67-81 行）
douyin_sign_obj = execjs.compile(open('libs/douyin.js').read())

def get_a_bogus_from_js(url, params, user_agent):
    return douyin_sign_obj.call("sign_datail", params, user_agent)
```

Go 等价实现：
```go
// 使用 go-execjs 或 os/exec 调用 Node.js
func generateABogus(url, params, userAgent string) (string, error) {
    cmd := exec.Command("node", "-e", fmt.Sprintf(`
        const sign = require('./libs/douyin.js');
        console.log(sign.sign_datail(%q, %q));
    `, params, userAgent))
    output, err := cmd.Output()
    return strings.TrimSpace(string(output)), err
}
```

### 2.6 MediaCrawler 的横切关注点模式

> **源码验证**：MediaCrawler 用 Mixin 模式处理横切关注点（代理轮换、重试逻辑）。

#### ProxyRefreshMixin（代理自动轮换）

```python
# proxy/proxy_mixin.py — 混入到每个 Client 类
class ProxyRefreshMixin:
    def init_proxy_pool(self, proxy_ip_pool):
        self._proxy_pool = proxy_ip_pool
        self._proxy_expire_at = 0

    async def _refresh_proxy_if_expired(self):
        if time.time() > self._proxy_expire_at:
            ip_info = await self._proxy_pool.get_proxy()
            self.proxy = format_proxy(ip_info)
            self._proxy_expire_at = time.time() + ip_info.expire_minutes * 60
```

每个 Client 都继承此 Mixin：
```python
class DouYinClient(AbstractApiClient, ProxyRefreshMixin):  # 抖音
class KuaiShouClient(AbstractApiClient, ProxyRefreshMixin):  # 快手
class BilibiliClient(AbstractApiClient, ProxyRefreshMixin):  # B站
```

**对 WebReaper 的启示**：Go 没有 Mixin，可以用组合模式实现：
```go
type ProxyRefreshMixin struct {
    pool      *ProxyPool
    proxy     string
    expireAt  time.Time
}

func (m *ProxyRefreshMixin) RefreshIfNeeded() error {
    if time.Now().Before(m.expireAt) {
        return nil
    }
    ip, err := m.pool.Get()
    if err != nil {
        return err
    }
    m.proxy = ip.Format()
    m.expireAt = time.Now().Add(ip.ExpireDuration)
    return nil
}

// 每个 Client 组合此 Mixin
type DouyinClient struct {
    ProxyRefreshMixin  // 组合，不是继承
    httpClient *http.Client
    // ...
}
```

### 2.7 WebReaper 迁移路径（从 XHR 方式到 httpx API 方式）

#### 当前实现 vs 目标实现

```
当前（WebReaper douyinweb）：
  chromedp 打开搜索页 → 等待 8 秒 → 页面内执行同步 XHR → 解析 JSON
  ❌ 每次搜索都要开新页面（8 秒等待）
  ❌ 依赖页面安全 SDK 上下文
  ✅ 不需要签名算法

目标（参考 MediaCrawler）：
  httpx 直接调用 API → 签名算法生成参数 → 解析 JSON 响应
  ✅ 毫秒级请求，无需页面渲染
  ✅ 资源消耗最小
  ❌ 需要维护签名算法（a_bogus）
```

#### 迁移步骤

**阶段 1：保持现有 XHR 方式，封装为 CrawlerPlatform 接口**

```go
// 暂时复用现有 douyinweb.Searcher 的 XHR 方式
// 封装为 CrawlerPlatform 接口，为后续迁移做准备
type DouyinCrawlerV1 struct {
    searcher *douyinweb.Searcher  // 复用现有实现
}

func (c *DouyinCrawlerV1) Search(ctx context.Context, opts SearchOptions) ([]CrawledVideo, error) {
    // 调用现有 SearchHotVideos，转换为 CrawledVideo
    videos, err := c.searcher.SearchHotVideos(ctx, tenantID, "douyin", opts.Keyword, opts.Limit)
    return convertToCrawledVideos(videos), err
}
```

**阶段 2：引入签名算法，实现 httpx API 客户端**

```go
// 引入 a_bogus 签名算法
// 实现 httpx 直接调用 API
type DouyinClient struct {
    httpClient *http.Client
    cookies    string
    userAgent  string
    msToken    string
}

func (c *DouyinClient) Search(ctx context.Context, keyword string, offset int) (*SearchResponse, error) {
    params := c.buildSearchParams(keyword, offset)
    params["a_bogus"] = c.generateABogus(params)  // 签名
    return c.get(ctx, DouyinSearchURL, params)
}
```

**阶段 3：切换到 httpx API 方式，XHR 作为降级**

```go
func (c *DouyinCrawler) Search(ctx context.Context, opts SearchOptions) ([]CrawledVideo, error) {
    // 优先级 1: httpx API 直接调用（快速）
    videos, err := c.client.Search(ctx, opts.Keyword, opts.Offset)
    if err == nil {
        return videos, nil
    }
    
    // 优先级 2: XHR 方式降级（慢但稳定）
    videos, err = c.xhrFallback.Search(ctx, opts)
    if err == nil {
        return videos, nil
    }
    
    // 优先级 3: 通用搜索引擎兜底
    return c.webSearchFallback.Search(ctx, opts)
}
```

### 2.7 各平台实现对比（源码验证版）

| 维度 | 抖音 | 快手 | B站 |
|------|------|------|-----|
| **数据获取** | httpx 直接调 API | httpx 直接调 REST API | httpx 直接调 API |
| **签名方式** | a_bogus（execjs 执行 JS） | __NS_hxfalcon（浏览器内 JS 执行） | wbi（算法纯 Go 可实现，但密钥需浏览器提取） |
| **浏览器用途** | 登录 + Cookie + msToken | 登录 + Cookie + 签名 JS 环境 | 登录 + Cookie + WBI 密钥提取 |
| **搜索端点** | `/aweme/v1/web/general/search/single/` | `/rest/v/search/feed` | `/x/web-interface/search/type` |
| **搜索是否需要签名** | ❌ 不需要 a_bogus | ✅ 需要 __NS_hxfalcon | ✅ 需要 wbi |
| **反爬强度** | 高 | 中 | 低 |
| **实现复杂度** | 中（搜索不需要签名） | 中（签名需浏览器） | 低（签名算法简单） |
| **WebReaper 现有基础** | 有（douyinweb） | 无 | 无 |

#### 重要发现：抖音搜索不需要 a_bogus 签名

**源码证据**（`douyin/client.py` 第 119 行）：

```python
if "/v1/web/general/search" not in uri:
    a_bogus = await get_a_bogus(uri, query_string, post_data, headers["User-Agent"], self.playwright_page)
    params["a_bogus"] = a_bogus
```

搜索端点 `/aweme/v1/web/general/search/single/` 包含 `/v1/web/general/search`，所以 a_bogus 被跳过。

**这意味着**：抖音搜索只需要 Cookie + msToken + 设备指纹，不需要签名算法。这大大简化了实现。

但视频详情、评论等其他端点仍然需要 a_bogus 签名。

### 4.4 三种爬取方式的技术选型

#### 方式 A：浏览器渲染爬取（Scrapy+Selenium 传统方式）

```
浏览器打开页面 → 等待渲染 → 解析 DOM → 提取数据
```

- ❌ 最慢（每次都要等页面渲染）
- ❌ 最容易被检测（webdriver 标记）
- ❌ 资源消耗大（每个页面都要渲染）

#### 方式 B：页面内 XHR 爬取（WebReaper 现有方案）

```
浏览器打开搜索页 → 注入 Cookie → 在页面内执行同步 XHR → 拿到 JSON
```

```go
// WebReaper 现有实现
func xhrSyncJS(url string) string {
    return `var xhr = new XMLHttpRequest();
            xhr.open('GET', '` + url + `', false); // 同步 XHR
            xhr.send();
            return xhr.responseText;`
}
```

- ✅ 不需要签名算法（XHR 在页面上下文中自动携带安全上下文）
- ⚠️ 每次搜索都要打开一个新页面（8 秒等待安全 SDK 初始化）
- ⚠️ 依赖页面的安全 SDK 上下文

#### 方式 C：API 直接调用（MediaCrawler 方案）

```
浏览器只拿 Cookie → 关闭浏览器 → httpx 直接调 API → 签名算法绕过
```

```python
# MediaCrawler 实现
a_bogus = execjs.compile(open('libs/douyin.js').read()).call("sign", params, ua)
resp = httpx.get("https://www.douyin.com/aweme/v1/web/general/search/single/",
    params={"keyword": "川菜", "a_bogus": a_bogus, "msToken": ms_token},
    cookies=cookies)
```

- ✅ 最快（直接 HTTP 请求，无需浏览器渲染）
- ✅ 资源消耗最小
- ❌ 需要逆向签名算法（a_bogus、x-s 等）
- ❌ 签名算法可能随平台更新失效

#### WebReaper 的技术选型：方式 B + 方式 C 混合

```
优先级 1: API 直接调用（方式 C）——如果签名算法可用
    ↓ 失败（签名失效/平台更新）
优先级 2: 页面内 XHR（方式 B）——WebReaper 现有方案，作为降级
    ↓ 失败（页面加载失败）
优先级 3: 通用搜索引擎（Bing/DDG）——最终兜底
```

**理由**：
- 方式 C 速度最快，但签名算法需要持续维护
- 方式 B 不需要签名，但速度较慢
- 两者互补：方式 C 为主，方式 B 降级

## 五、管理后台动态控制设计

### 5.1 配置热生效机制

```
管理后台修改配置
  → API 保存到 crawler_configs 表
  → CrawlerManager.UpdateConfig() 被调用
  → 内存中的 CrawlerConfig 热更新
  → 下次定时任务执行时使用新配置
  → 无需重启服务
```

### 5.2 分时段轮流爬取调度器

```
调度器设计（参考 MediaCrawler 的定时任务模式）：

品牌队列管理：
  - 所有品牌的采集配置按 sort_order 排序
  - 维护一个"下次执行时间"指针
  - 每次定时触发：取出队列头部的品牌 → 执行采集 → 移到队尾

执行节奏：
  - 基础间隔：每 15 分钟处理一个品牌
  - 可配置：管理后台可调整间隔（5-60 分钟）
  - 夜间加速：00:00-06:00 间隔缩短为 5 分钟（夜间请求少，风控松）

账号轮换策略：
  - 每处理 N 个品牌切换一次账号（默认 N=3）
  - 切换时检查新账号健康状态
  - 所有账号不可用时暂停队列，通知管理员

失败处理：
  - 单个品牌失败：跳过，加入重试队列
  - 连续失败 3 次：暂停该品牌，标记 need_attention
  - 所有品牌失败：暂停整个队列，通知管理员

示例时间线（假设 6 个品牌，15 分钟间隔）：
  06:00 品牌A → 账号1 → 成功 → 入库 20 条
  06:15 品牌B → 账号1 → 成功 → 入库 18 条
  06:30 品牌C → 账号1 → 成功 → 入库 22 条
  06:45 品牌D → 账号2（切换）→ 成功 → 入库 15 条
  07:00 品牌E → 账号2 → 失败 → 加入重试队列
  07:15 品牌F → 账号2 → 成功 → 入库 19 条
  07:30 品牌A（第二轮）→ 账号2 → 刷新指标
  ...
```

### 5.3 任务监控

```
定时任务执行
  → 创建 crawler_task_logs 记录（status=running）
  → 执行采集逻辑
  → 更新记录（status=success/failed, videos_found, duration_ms）
  → 管理后台可实时查看
```

### 5.3 Cookie 管理

```
管理后台 → Cookie 管理页面
├── 查看所有平台的 Cookie 状态
├── Cookie 过期提醒
├── 一键刷新 Cookie（打开浏览器重新登录）
└── Cookie 账号选择（多账号轮换）
```

## 七、风险与缓解

| 风险 | 影响 | 缓解措施 | 参考 MediaCrawler 的做法 |
|------|------|----------|------------------------|
| **平台方账号被封** | 该平台数据采集中断 | 多账号轮换 + 代理隔离 + 频率限制 + 健康检查自动切换 | `ProxyRefreshMixin` 自动轮换 |
| **Cookie 频繁过期** | 爬取失败 | 定时健康检查（30 分钟）+ 管理后台提醒 + 扫码刷新 | 抖音发布后回写 Cookie |
| **签名算法失效** | API 调用被拒绝 | 降级到 XHR 方式；监控签名成功率 | `douyin.js` 需要持续维护 |
| **CDP 连接不稳定** | 爬虫失败 | 自动重连 + CDP→标准模式降级 | 所有平台 `core.py` 都有此降级 |
| **平台 API 变更** | 端点失效 | 监控错误率 + 快速修复 + 降级到通用搜索 | 各平台独立降级策略 |
| **数据量增长** | 存储压力 | 30 天自动清理 + 按品牌分页 | — |
| **代理 IP 被封** | 请求被拒 | 代理池轮换 + 每账号独立代理 + 失效自动更换 | — |

### 账号安全策略

```
风险控制三层防护：

第一层：频率控制
  - 每账号每日使用上限（默认 50 次）
  - 每次请求间隔（默认 2 秒）
  - 同一账号连续使用后冷却（10 分钟）

第二层：代理隔离
  - 每个平台方账号绑定独立代理 IP
  - 代理失效自动更换
  - 不同账号不共享代理

第三层：健康监控
  - 每 30 分钟自动健康检查
  - 异常账号自动停用
  - 管理后台实时告警
  - 所有账号都不可用时通知管理员
```
