# 32 号设计：作品管理（admin 侧）与内容安全闭环

> 日期：2026-09-01
> 背景：15 号梳理缺口 #2——作品域无 admin 管理端点（不能查看/删除/重发布用户作品）。用户定调：**用户的内容不能脱离管理，违规内容影响平台运营**。
> 关联：31 号（音色物化，已实施）、05 号（发布域——拦截点）。

---

## 一、现状事实（决定设计方向）

| # | 事实 | 证据 |
|---|------|------|
| 1 | **作品无独立表**——是聚合视图：文章=OptimizedContent、成片=GenerationTask(success+deliverable)、发布态=PublishJob、互动=video_metrics | works.go:1-14（三源合并注释）、ListWorks 聚合 |
| 2 | 文章侧**已有** admin 管理：`GET /admin/contents`（全平台内容一览）+ `POST /admin/contents/:id/status`（发布/下架）+ `DELETE` | router_admin.go |
| 3 | 成片侧**零管理**：GenerationTask 无任何 admin 端点；用户端作品聚合无过滤通道 | router_admin.go 无 works/task 管理端点 |
| 4 | 发布是内容出口：`POST /merchant/publish` 目前不校验作品是否被平台处置 | account.go Publish 流程 |

**推论**：缺口实质 = **成片（GenerationTask 产物）的管理通道** + **聚合过滤** + **发布拦截**。文章侧复用现状即可。

## 二、方案：处置表 + 聚合过滤 + 发布拦截

### 2.1 数据层——独立处置表（不动业务核心表）

```sql
-- 086_work_moderations.sql
CREATE TABLE work_moderations (
  id         VARCHAR(64) PRIMARY KEY,
  work_key   VARCHAR(64) NOT NULL UNIQUE,  -- g-{taskID}（成片）/ c-{contentID}（文章）——与 WorksUseCase 的 WorkItem.ID 同构
  work_kind  VARCHAR(16) NOT NULL,         -- article / video / image / audio
  tenant_id  VARCHAR(64) NOT NULL,         -- 归属租户（跨租户巡查定位）
  action     VARCHAR(16) NOT NULL,         -- hidden（下架：用户端不可见）/ deleted（逻辑删除：不可见+不可发布）
  reason     VARCHAR(512) NOT NULL DEFAULT '',
  operator   VARCHAR(64) NOT NULL DEFAULT '', -- admin 操作者（审计）
  created_at DATETIME(3), updated_at DATETIME(3),
  UNIQUE KEY uk_work (work_key)
);
```

**为什么独立表而不是给 generation_tasks 加列**：下架是**运营动作**不是任务属性——管理语义（原因/操作者/时间/恢复）与生成域解耦；统一覆盖 article+video 两类 work_key；将来审计/申诉/机审结果都落这张表。物理不删 GenerationTask（溯源留痕），"删除"=最高处置标记。

### 2.2 聚合过滤（用户端）

`WorksUseCase.ListWorks` 注入 `WorkModerationRepository`（可选）：
- 查本租户 hidden/deleted 的 work_key 集合 → 聚合结果剔除；
- 作品详情/预填跳发布路径同样过滤（防从详情页绕过）。

### 2.3 Admin API（P0 全量）

| 端点 | 方法 | 功能 |
|------|------|------|
| `/admin/works` | GET | 跨租户作品巡查流：聚合全平台作品（复用 WorksUseCase 扩展 admin 变体）+ 筛选（tenant_id/kind/时间/关键词/仅看已处置）+ 分页 |
| `/admin/works/:key/hide` | POST | 下架（body: reason 必填）——用户端即刻不可见 |
| `/admin/works/:key/restore` | POST | 恢复（清处置记录） |
| `/admin/works/:key` | DELETE | 逻辑删除（action=deleted；比 hidden 多一层"不可再发布"语义） |

错误语义：work_key 不存在 → "作品不存在"；重复处置 → 幂等更新（覆盖 action/reason/operator）。

### 2.4 发布拦截（P1——防扩散，比删除更重要）

`POST /merchant/publish` 提交校验链新增一步：
- 文章类：content_id → work_key `c-{id}` 查处置表；
- 多媒体类：media_urls 反查 deliverable 任务 → work_key `g-{taskID}` 查处置表；
- 命中 hidden/deleted → 拒绝："该作品已被平台处置，无法发布"。
- RPA 全自动通道同一校验（发布执行前再查一次，防提交后处置的竞态）。

### 2.5 前端（P0 最小面）

商户与品牌页（/admin/tenants）新增 **Works Tab**：
- 默认视图 = 最新作品巡查流（缩略图/标题/租户/类型/发布状态）；
- 行操作：预览（播放器/原文）→ 下架（弹窗填原因，必填）/ 恢复 / 删除；
- 筛选条：租户/类型/时间段/仅看已处置。

### 2.6 分层实施

| 批次 | 内容 | 价值 |
|------|------|------|
| P0 | 086 迁移 + 处置仓储 + GET /admin/works + hide/restore + 聚合过滤 + 前端 Works Tab | **合规保底**：违规内容可发现、可下架、用户端即刻消失 |
| P1 | 发布拦截（publish 前置校验 + RPA 执行前复检）+ DELETE + 操作审计查询 | **防扩散**：处置过的内容换入口也发不出去 |
| P2 | 机审接入：成片提交/文案生成时 MiMo LLM 审核提示词预筛 → 可疑进巡查队列置顶 | 规模化：人工巡查 → 机审+人工复核 |
| P2+ | 申诉流（用户提交申诉→admin 复核）| 运营完善项 |

## 三、设计权衡记录

| 备选 | 否决理由 |
|------|---------|
| 给 generation_tasks 加 admin_hidden 列 | 管理语义泄漏进生成域核心表；文章类覆盖不到；审计字段（原因/操作者）没地方放 |
| 物理删除任务/内容行 | 破坏溯源（B-Roll 血缘/发布关联断链）；不可恢复风险 |
| 只做发布拦截不做下架 | 用户端仍可见违规内容（作品库展示本身就是影响面） |
| 重建独立作品表 | 聚合视图是正确设计（三源一致性免维护）；管理通道用处置表叠加即可，不重复存储 |

## 四、测试清单

- 处置 CRUD 幂等（重复 hide 覆盖）；
- 聚合过滤：hidden/deleted 作品从用户列表/详情/预填路径消失；restore 恢复；
- 发布拦截：文章/多媒体两路命中拒绝；未处置放行；RPA 通道执行前复检；
- 越权：work_key 跨租户隐藏无影响（处置表本身全局，按 key 唯一）；
- 审计：hide/restore/delete 记录 operator+reason。
